# Feature tour site

The feature tour is a static GitHub Pages site that shows a screenshot and an explanation for every feature in the Microsoft AI Training Generator catalog, plus a guided tour that steps through them. It covers all six products:

| Product id | Product | Where on the site |
| --- | --- | --- |
| `copilot-studio` | Microsoft Copilot Studio (Standard harness, Microsoft Copilot harness, Customer Conversation harness) | the site root |
| `m365-copilot-agent-builder` | Agent Builder and declarative agents for Microsoft 365 Copilot | `m365-copilot-agent-builder/` |
| `sharepoint-ai` | SharePoint AI features | `sharepoint-ai/` |
| `ai-foundry` | Microsoft Foundry | `ai-foundry/` |
| `m365-copilot-hub` | Microsoft 365 Copilot hub and Copilot controls | `m365-copilot-hub/` |
| `power-platform-ai-hub` | Power Platform AI hub (AI Builder) | `power-platform-ai-hub/` |

Copilot Studio is the only product with harnesses, so only its pages show the harness badge and filter; the other products group features by category. Every product reads the catalog in [`portal/lib/lab-builder/features.json`](../portal/lib/lab-builder/features.json) (Copilot Studio) and `portal/lib/lab-builder/catalog/<product>.json` (the rest). It does not cover the lab portal's own features.

- **Overview**: filter and search by level, category, availability, and screenshot status (and by harness for Copilot Studio). A **Products** row links the six tours.
- **Feature pages**: one per feature, with what it is, why it matters, where to click, prerequisites, caveats, how to check your work, Microsoft Learn links, and screenshots with numbered callouts.
- **Guided tour**: every feature in order (harness, then category, then level for Copilot Studio; category, then level for the rest) with Previous and Next, a progress bar, deep links such as `tour.html#mc-skills`, and keyboard support (Left and Right arrows, Home, End).
- Screenshots that have not been captured yet show a clear **Screenshot pending** placeholder that says what the screenshot will show. The tour works the same either way.

Everything is generated by `tools/feature-tour/`, so the site stays in sync with the catalog. There are no external scripts, fonts, or trackers.

Nothing in this repository can sign in to a tenant for you, and the tools never fabricate images. The Copilot Studio labs under `labs/` have their own real screenshots (157 PNGs); those are separate and unchanged. Run `npm run capture:status` for the current counts.

## How the pieces fit

```text
portal/lib/lab-builder/features.json         Copilot Studio features (single source of truth)
portal/lib/lab-builder/catalog/<product>.json  the other five products' features
portal/lib/lab-builder/screenshot-slots.json reviewed alt text and caption for every screenshot filename
tools/feature-tour/capture-products.json     per product: start URL, browser profile, and where each portal area lives
tools/feature-tour/overlay.json              curated additions: shots for features that have none, shot overrides, caveats
              |
              v   npm run feature-tour:build
tools/screenshot-capture/feature-shots.json                 generated shot list, Copilot Studio (commit it)
tools/screenshot-capture/feature-shots.<product>.json       generated shot list, one per other product (commit them)
_site/                                                      generated site (not committed; the workflow builds and deploys it)

docs/feature-tour/screenshots/         your captured PNGs and the <name>.callouts.json files the capture tool writes, for every product
```

The build reads the screenshots folder. A shot counts as captured when its file is a real PNG, JPEG, or WebP of at least 5 KB, the same bar the capture tool applies. Anything else stays pending. After you commit real screenshots, the next build picks them up with no code changes. All products share one folder, so every screenshot filename belongs to exactly one shot.

### Captured images reach generated labs automatically

A lab built with the lab builder (portal or `npm run build-lab`) uses the same filenames for its screenshot slots. When a slot's file exists in `docs/feature-tour/screenshots/` as a real image, the generator copies it into the lab's `assets/` folder instead of writing the "Screenshot pending" placeholder; every other slot keeps the placeholder. The lab's Markdown, alt text, and caption are the same either way, so nothing needs editing when an image arrives. The portal's lab preview also shows a captured image for a lab generated earlier, the next time the lab is opened. Set `FEATURE_TOUR_SCREENSHOTS_DIR` to read captures from another folder.

## One-time setup: enable GitHub Pages

The workflow `.github/workflows/feature-tour-pages.yml` deploys the site, but a repository admin must turn Pages on once:

1. Open the repository **Settings** > **Pages**.
2. Under **Build and deployment**, set **Source** to **GitHub Actions**.
3. Run the **Publish feature tour to GitHub Pages** workflow from the **Actions** tab (or push a change to a watched path on `main`).

The site is then at `https://<owner>.github.io/<repo>/`. All links in the site are relative, so the project path works.

The workflow runs on pushes to `main` that touch the catalog, `tools/feature-tour/`, the shot lists, `docs/feature-tour/`, or the workflow itself, and on manual dispatch. It refuses to deploy if a shot list is stale or the tests fail.

## Refresh the content

When the catalog changes (new feature, new steps, new Learn links, a changed level or availability) or `capture-products.json` changes:

```powershell
npm run feature-tour:build     # regenerates every feature-shots*.json and _site/
npm run feature-tour:test      # node --test for the generator, shot lists, and site
npm run feature-tour:serve     # preview at http://127.0.0.1:8080/
```

Commit every `tools/screenshot-capture/feature-shots*.json` file that changed. `npm run feature-tour:check` (and CI) fails if you forget, if a manifest is missing, or if one no longer belongs to a product. `node tools/feature-tour/build.mjs --check --product=<id>` checks one product.

Content comes straight from the catalog: summary, why it matters, concepts, the numbered steps (taken from the cited Learn procedure), prerequisites, validation checks, `harnessNote`, availability, Learn URLs, and `lastVerified` / `verifiedAgainst`. Bold names in the steps are the UI elements the page lists under "UI elements you will use". Nothing is invented: when the catalog has no availability label, the site says "Not flagged" instead of guessing. Each shot's caption and alt text come from `screenshot-slots.json`, the same text the generated labs use.

### Capture settings per product

[`tools/feature-tour/capture-products.json`](../tools/feature-tour/capture-products.json) says where each product's screens are:

| Key | Use |
| --- | --- |
| `authProfile` | The browser profile folder under `tools/screenshot-capture/.auth/`, so you sign in once per product and tenant. |
| `startUrl`, `startUrlEnv` | The page the capture browser opens first, and the environment variable that overrides it with a tenant-specific address. |
| `sections.<section>.url` | A public sign-in or home page, quoted from Microsoft Learn. A location Learn gives no stable address for has no URL. |
| `sections.<section>.urlEnv` | An environment variable holding a tenant-specific address (a SharePoint site, a Foundry project). It wins over `url`. |
| `sections.<section>.hint` | Where the screen is, printed before each shot. |
| `sections.<section>.manual` | The screen is outside the browser (a terminal or Visual Studio Code); you capture it with an OS screenshot tool. |

A catalog screenshot whose `section` has no entry here makes `npm run feature-tour:build` fail, so a new area cannot be added without saying where it lives.

### Overlay

[`tools/feature-tour/overlay.json`](../tools/feature-tour/overlay.json) holds the few things the catalog does not carry:

| Key | Use |
| --- | --- |
| `shots.<featureId>[]` | Screenshot entries (`filename`, `section`, `caption`, `instructions`, `callouts`) for features whose catalog entry has none. |
| `shotOverrides.<filename>` | Replace the caption, instructions, callouts, or `manual` flag of a catalog shot once you have seen the real screen. |
| `features.<featureId>` | Extra `caveats`, or a `uiPath` list that replaces the derived UI elements. |

A callout is `{ "label": "Instructions", "text": "Instructions", "note": "What to know" }`. `text` is the visible UI text the capture tool looks for to place the numbered hotspot. The sidecar `<name>.callouts.json` works the same for every product.

A Copilot Studio feature with no shot anywhere still gets a default slot (`<id>-main.png`), so a new feature can never silently drop off the site. Replace it with a curated shot in the overlay.

## Capture the real screenshots

Capturing needs you, because it signs in to your own tenants. The tool never stores credentials in the repository; each browser profile lives in the git-ignored `tools/screenshot-capture/.auth/<product>` folder. Use test tenants and test environments, never production, and never show real customer data, tenant names, user names, or secrets in a screenshot.

### Set up the tool once

Node.js 24 or later, then:

```powershell
cd tools/screenshot-capture
npm ci
npx playwright install chromium
```

### See what is left

```powershell
npm run capture:status                       # from the repository root: captured and pending per product
node tools/screenshot-capture/status.mjs --product=sharepoint-ai   # per feature for one product
```

The report ends with the exact command to run next and any tenant addresses to set first. Preview any run without opening a browser by adding `--dry-run`:

```powershell
cd tools/screenshot-capture
node capture.js --features --dry-run                      # every product
node capture.js --product=sharepoint-ai --dry-run --section=sharepoint-admin-center
```

### Capture commands

```powershell
cd tools/screenshot-capture
node capture.js --product=<id> --missing                      # one product, only what is missing
node capture.js --product=<id> --section=<area> --missing     # one portal area (see --list for the section names)
node capture.js --product=<id> --feature=<feature-id>         # one feature
node capture.js --product=<id> --only=12                      # one shot id
node capture.js --product=<id> --all --feature=<feature-id>   # re-capture
node capture.js --product=all --missing                       # every product in turn
```

`--features` alone means `--product=copilot-studio`, and with `--list` or `--dry-run` it covers every product. Shot ids are per product and shift when the catalog changes, so prefer `--section` and `--feature`. npm 11 drops unknown flags from `npm run ... -- --flag`, so pass flags to `node capture.js` directly.

### What happens for each shot

1. The tool opens Chromium with the product's own profile at the product's start page. The first time, sign in; the session is cached for next time.
2. For each shot it navigates to the shot's address when it has one (a tenant address from its environment variable wins), prints the steps to reach the screen, what the screenshot must show, and the numbered callouts it will look for.
3. You set up the screen, then press **Space** to snap, **r** to retry, **n** to skip, **q** to quit.
4. It saves `docs/feature-tour/screenshots/<filename>` and a `<name>.callouts.json` with the position of each callout (fractions of the viewport). Callouts whose text was not visible are reported; reveal them and press **r**, or accept that they appear in the list only.

A shot marked **manual** (a terminal, or Visual Studio Code for Agents Toolkit) is not screenshotted by the tool. Capture it with an OS screenshot tool, save it as PNG at the printed path, and press **Space** so the tool verifies it. You can write a `<name>.callouts.json` by hand if you want numbered callouts on it. Capture at the default 1440 by 900 viewport.

### Tenant-specific addresses

Set these in the same terminal before you run the capture command. All must be `https` URLs; anything else is rejected.

| Variable | Used for |
| --- | --- |
| `CAPTURE_COPILOT_STUDIO_START_URL` | Copilot Studio start page, for a regional or government host. |
| `CAPTURE_M365_AGENT_BUILDER_START_URL` | Agent Builder start page. |
| `CAPTURE_SHAREPOINT_AI_START_URL` | SharePoint AI start page. |
| `CAPTURE_SHAREPOINT_SITE_URL` | A SharePoint site you own (site, library, and agent builder shots). |
| `CAPTURE_SHAREPOINT_ADMIN_URL` | `https://<TenantName>-admin.sharepoint.com` (SharePoint admin center shots). |
| `CAPTURE_M365_ADMIN_URL` | A Microsoft 365 admin center address if you need a specific one. |
| `CAPTURE_FOUNDRY_START_URL` | Foundry start page. |
| `CAPTURE_FOUNDRY_PROJECT_URL` | Your Foundry project page, copied from the address bar (project and agent shots). |
| `CAPTURE_M365_COPILOT_HUB_START_URL` | Copilot hub start page. |
| `CAPTURE_POWER_PLATFORM_START_URL` | Your Power Platform environment, for example `https://make.powerapps.com/environments/<environment-id>/home`. |

```powershell
$env:CAPTURE_SHAREPOINT_SITE_URL = "https://<TenantName>.sharepoint.com/sites/<site>"

```

### Per-product guide

Prerequisite wording is taken from each product's entry in `portal/lib/lab-builder/products.json`, which quotes Microsoft Learn. Where Learn does not say, this guide says **Not confirmed in Microsoft Learn** rather than guessing. Capture the areas in the order listed so you stay in one portal at a time.

#### 1. Copilot Studio (`copilot-studio`, 136 shots)

- **Tenant and licenses**: a tenant where you can create agents in a test environment; a Copilot Studio license or trial.
- **Roles**: permission to create agents; an admin role for the Power Platform admin center shots.
- **Harnesses and preview**: the Microsoft Copilot harness enabled for your environment and user so the **Build** and **Preview** tabs appear (see [Harnesses in Copilot Studio](https://learn.microsoft.com/microsoft-copilot-studio/harnesses-overview)); the Standard harness through **Open classic experience** on the Home page. Features marked Preview can need a preview-enabled environment; capture them when you have access and skip the rest.
- **Sample data**: one agent with a few topics, a SharePoint site or files for knowledge, an MCP server URL, a published agent flow or workflow, an Excel workbook for the created-files demo. Integrations with outside systems (ServiceNow, Snowflake, SAP, Salesforce, Jira, Epic on FHIR, Shopify) need an account there; skip those shots with `n` and they stay pending.
- **Order**: `--harness=standard`, then `--harness=both`, then `--harness=microsoft-copilot`, each with `--missing`. Start the browser from Home (`https://copilotstudio.microsoft.com`), open your agent once, and the tool jumps to the agent's Topics, Settings, Agents, and Evaluations pages itself.

#### 2. Agent Builder and declarative agents (`m365-copilot-agent-builder`, 43 shots)

- **Tenant and licenses**: a Microsoft 365 Copilot license, or a tenant with pay-as-you-go billing enabled for Copilot Studio (agent capabilities vary by billing model).
- **Roles**: for Agents Toolkit, an admin who enabled the **Upload custom apps** toggle (Teams admin center > Teams apps > Setup policies > Global (Org-wide default)). Government cloud support varies; see the declarative agents overview on Microsoft Learn.
- **Tools**: Visual Studio Code with the Microsoft 365 Agents Toolkit extension for the Agents Toolkit shots. Those are manual shots: capture them with an OS screenshot tool.
- **Sample data**: an agent you build with non-sensitive names; mask any sensitive text in test prompts and answers.
- **Order**: `--section=build`, `--section=knowledge`, `--section=test`, `--section=deploy` (Microsoft 365 Copilot at `https://m365.cloud.microsoft/chat`), then `--section=admin` (Teams admin center, `https://admin.teams.microsoft.com/`).

#### 3. SharePoint AI (`sharepoint-ai`, 31 shots)

- **Tenant and licenses**: a Microsoft 365 tenant with SharePoint Online and a user with an active Microsoft 365 Copilot license. Everyday Copilot in SharePoint capabilities are included with that license; advanced work uses Copilot Credits through usage-based billing.
- **Roles**: a SharePoint site and a document library you own; for admin shots, SharePoint administrator access. Exact roles for SharePoint Advanced Management: **Not confirmed in Microsoft Learn**.
- **Preview**: Learn states Copilot in SharePoint is in public preview with general availability starting to roll out on September 30, 2026, so a feature can be missing from your tenant. Government clouds and 21Vianet are not supported.
- **Sample data**: a test site with a few documents, a library for the autofill shots, and a SharePoint knowledge source for the agent shots.
- **Set first**: `CAPTURE_SHAREPOINT_SITE_URL` and `CAPTURE_SHAREPOINT_ADMIN_URL` (see above).
- **Order**: `--section=sharepoint-site`, `--section=sharepoint-library`, `--section=agent-builder`, `--section=copilot-app`, then the admin areas `--section=sharepoint-admin-center` and `--section=m365-admin-center`. Last, `--section=powershell` (manual: run the command in SharePoint Online Management Shell, remove the tenant name from the output, and save the image).

#### 4. Microsoft Foundry (`ai-foundry`, 38 shots)

- **Tenant and licenses**: an Azure account with an active subscription. The platform is free to explore; pricing occurs at the deployment level and the underlying services incur costs.
- **Roles**: a role that can create a Foundry resource, such as Foundry Account Owner or Foundry Owner on the subscription or resource group.
- **Portal toggle**: `https://ai.azure.com` with the **New Foundry** toggle on for Foundry projects and off for hub-based projects in Foundry (classic).
- **Quota**: model and agent shots need quota and a supported region for the chosen model. Which region works for every model: **Not confirmed in Microsoft Learn**.
- **Sample data**: a test project, one model deployment, one agent, and a small evaluation dataset with no real data.
- **Set first**: `CAPTURE_FOUNDRY_PROJECT_URL` (copy your project's address).
- **Order**: `home`, `catalog`, `playground`, `agents`, `manage`, `evaluation`, `guardrails`, `publish`, `microsoft-copilot`, `copilot-studio` (each as `--section=<name>`); then `azure-portal` (`https://portal.azure.com`), then `classic-portal` with the toggle off. Last, `local` (manual terminal shots); some `agents` shots also run in a terminal, so use `n` and capture those manually.

#### 5. Microsoft 365 Copilot hub (`m365-copilot-hub`, 33 shots)

- **Tenant and licenses**: a Microsoft 365 tenant with an eligible prerequisite plan and Microsoft Copilot licenses to assign (see License options for Microsoft Copilot on Microsoft Learn).
- **Roles**: the AI Administrator role for Copilot and agent settings, plus License Administrator or User Administrator to assign licenses. Global Reader or AI Reader can view but not change. Roles for Microsoft Purview and the SharePoint admin center: **Not confirmed in Microsoft Learn**.
- **Sample data**: a test group and a few test users for license assignment shots; a Copilot interaction so Audit and reports have activity (reports can lag).
- **Order**: `--section=admin-center` (`https://admin.cloud.microsoft/`), `m365-apps-admin-center` (`https://config.office.com/`), `sharepoint-admin-center`, `purview` (`https://purview.microsoft.com`), then `copilot-app`.

#### 6. Power Platform AI hub (`power-platform-ai-hub`, 44 shots)

- **Tenant and licenses**: a Power Platform environment with a Microsoft Dataverse database and AI Builder enabled; a license that lets you create an environment, plus Copilot Credits or AI Builder credits to run models and prompts. Building and testing custom models and prompts does not require credits. AI Builder credits are progressively ending as features move to Copilot Credits.
- **Roles**: sign in to `https://make.powerapps.com` or `https://make.powerautomate.com` with the Environment Maker role (or System Administrator or System Customizer). Regions where prompts are available: **Not confirmed in Microsoft Learn**.
- **Sample data**: a test environment, a small Dataverse table or sample documents for models and prompts, a flow, and a canvas app with a button.
- **Set first**: `CAPTURE_POWER_PLATFORM_START_URL` to your environment's Power Apps address.
- **Order**: `--section=ai-hub`, `prompt-builder`, `power-apps`, `power-automate` (`https://make.powerautomate.com`), `admin-center` (`https://admin.powerplatform.microsoft.com/`), then `learn` (a Microsoft Learn page shot; open the article named in the steps).

### After capturing

```powershell
npm run feature-tour:verify    # captured and pending per product; fails on invalid files or sidecars
npm run feature-tour:build
npm run feature-tour:serve     # check the pages and the tour in a browser
git add docs/feature-tour/screenshots
```

Commit and push. The workflow rebuilds the site; captured shots replace their placeholders and the callouts become hotspots, with no code changes. New labs generated for any product pick the same images up. `node tools/screenshot-capture/verify-shots.js --features --strict-missing` makes pending screenshots a failure if you want a hard gate once everything is captured; add `--product=<id>` for one product.

If a callout lands on the wrong element, add a `shotOverrides` entry with a more specific `text`, then re-capture that shot.

## Add a feature or a product

- **A feature**: add it to `portal/lib/lab-builder/features.json` (Copilot Studio) or `catalog/<product>.json` following [Lab builder: extending the catalog](lab-builder.md). Run `npm run feature-tour:build`; the feature appears on the overview, in the tour, and in its product's shot list. Commit the catalog change and the regenerated `feature-shots*.json`. If its screenshots use a new `section`, add that section to `capture-products.json` first.
- **A product**: add it to `products.json` and `catalog/<product>.json` as described in the lab builder guide, add its entry to `capture-products.json` (`order`, `label`, `authProfile`, `startUrl`, `startUrlEnv`, `sections`), and run the build. It gets its own shot list, site section, and browser profile.
- Optional: add curated shots to `overlay.json` for a better capture plan.

## Tests and checks

| Command | What it checks |
| --- | --- |
| `npm run feature-tour:test` | Every feature of every product appears exactly once; every catalog feature has a slot; filenames are unique across products; harness, level, and availability match; Learn links are well formed; no earlier harness name or British spelling; placeholder versus captured detection; captured images and sidecars reach each product's pages; shot list schema; `--check` catches a stale, missing, or unexpected shot list; accessibility basics and WCAG AA color contrast. |
| `npm run feature-tour:check` | Every committed shot list matches the catalog, overlay, and capture settings. |
| `npm run feature-tour:verify` | Captured and pending screenshots per product, invalid images, orphan files. |
| `node --test "tools/screenshot-capture/test/*.test.mjs"` | `capture.js --dry-run` for each product, `--section`, tenant-address variables, `verify-shots.js` pending, strict, and stub behavior, and the status report. |

All tests are hermetic: they use temporary fixture images and never contact a tenant. The same checks run in the **Validate content and tooling** workflow.

## Terminology

Use "Microsoft Copilot harness" everywhere it applies, which is only Copilot Studio. Some Learn pages and URLs still use an earlier name, so you may see it in a link; do not copy it into site text.
