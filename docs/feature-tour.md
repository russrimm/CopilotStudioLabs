# Feature tour site

The feature tour is a static GitHub Pages site that shows a screenshot and an explanation for every Copilot Studio feature in the lab builder catalog, plus a guided tour that steps through them. It covers the features in [`portal/lib/lab-builder/features.json`](../portal/lib/lab-builder/features.json) across the Standard harness and the Microsoft Copilot harness. It does not cover the lab portal's own features.

- **Overview**: filter and search by harness, level, category, availability, and screenshot status.
- **Feature pages**: one per feature, with what it is, why it matters, where to click, prerequisites, caveats, how to check your work, Microsoft Learn links, and screenshots with numbered callouts.
- **Guided tour**: every feature in order (harness, then category, then level) with Previous and Next, a progress bar, deep links such as `tour.html#mc-skills`, and keyboard support (Left and Right arrows, Home, End).
- Screenshots that have not been captured yet show a clear **Screenshot pending** placeholder that says what the screenshot will show. The tour works the same either way.

Everything is generated by `tools/feature-tour/`, so the site stays in sync with the catalog. There are no external scripts, fonts, or trackers.

## How the pieces fit

```text
portal/lib/lab-builder/features.json   single source of truth (read only here)
tools/feature-tour/overlay.json        curated additions: shots for features that have none, shot overrides, caveats
              |
              v   npm run feature-tour:build
tools/screenshot-capture/feature-shots.json   generated shot list (commit it)
_site/                                        generated site (not committed; the workflow builds and deploys it)

docs/feature-tour/screenshots/         your captured PNGs and the <name>.callouts.json files the capture tool writes
```

The build reads the screenshots folder. A shot counts as captured when its file is a real PNG, JPEG, or WebP of at least 5 KB, the same bar the capture tool applies. Anything else stays pending. After you commit real screenshots, the next build picks them up with no code changes.

## One-time setup: enable GitHub Pages

The workflow `.github/workflows/feature-tour-pages.yml` deploys the site, but a repository admin must turn Pages on once:

1. Open the repository **Settings** > **Pages**.
2. Under **Build and deployment**, set **Source** to **GitHub Actions**.
3. Run the **Publish feature tour to GitHub Pages** workflow from the **Actions** tab (or push a change to a watched path on `main`).

The site is then at `https://<owner>.github.io/<repo>/`. All links in the site are relative, so the project path works.

The workflow runs on pushes to `main` that touch the catalog, `tools/feature-tour/`, the shot list, `docs/feature-tour/`, or the workflow itself, and on manual dispatch. It refuses to deploy if the shot list is stale or the tests fail.

## Refresh the content

When the catalog changes (new feature, new steps, new Learn links, a changed level or availability):

```powershell
npm run feature-tour:build     # regenerates feature-shots.json and _site/
npm run feature-tour:test      # node --test for the generator, shot list, and site
npm run feature-tour:serve     # preview at http://127.0.0.1:8080/
```

Commit `tools/screenshot-capture/feature-shots.json`. `npm run feature-tour:check` (and CI) fails if you forget.

Content comes straight from the catalog: summary, why it matters, concepts, the numbered steps (taken from the cited Learn procedure), prerequisites, validation checks, `harnessNote`, availability, Learn URLs, and `lastVerified` / `verifiedAgainst`. Bold names in the steps are the UI elements the page lists under "UI elements you will use". Nothing is invented: when the catalog has no availability label, the site says "Not flagged" instead of guessing.

### Overlay

[`tools/feature-tour/overlay.json`](../tools/feature-tour/overlay.json) holds the few things the catalog does not carry:

| Key | Use |
| --- | --- |
| `shots.<featureId>[]` | Screenshot entries (`filename`, `section`, `caption`, `instructions`, `callouts`) for features whose catalog entry has none. |
| `shotOverrides.<filename>` | Replace the caption, instructions, or callouts of a catalog shot once you have seen the real screen. |
| `features.<featureId>` | Extra `caveats`, or a `uiPath` list that replaces the derived UI elements. |

A callout is `{ "label": "Instructions", "text": "Instructions", "note": "What to know" }`. `text` is the visible UI text the capture tool looks for to place the numbered hotspot.

A feature with no shot anywhere still gets a default slot (`<id>-main.png`), so a new feature can never silently drop off the site. Replace it with a curated shot in the overlay.

## Capture the real screenshots

Capturing needs you, because it signs in to your Copilot Studio tenant. The tool never stores credentials in the repository; the browser profile lives in the git-ignored `tools/screenshot-capture/.auth` folder.

### Before you start

- **Tenant and access**: a Copilot Studio tenant where you can create agents in a test (not production) environment.
- **Microsoft Copilot harness**: enabled for your environment and user, so the **Build** and **Preview** tabs appear. See [Harnesses in Copilot Studio](https://learn.microsoft.com/microsoft-copilot-studio/harnesses-overview).
- **Standard harness**: reachable through **Open classic experience** on the Home page.
- **Preview features**: features the catalog marks Preview (see the Preview badge on the site) can need a preview-enabled environment. Capture them when you have access and skip the rest.
- **Test data** that the screens need: one agent with a few topics, a SharePoint site or files for knowledge, an MCP server URL, a published agent flow or workflow, an Excel workbook for the created-files demo, and an admin role for the Power Platform admin center shots. Integrations with outside systems (ServiceNow, Snowflake, SAP, Salesforce, Jira, Epic on FHIR, Shopify) need an account there; if you do not have one, skip those shots with `n` and they stay pending.
- **Tools**: Node.js 24 or later, then install once:

```powershell
cd tools/screenshot-capture
npm ci --registry https://packagefeedproxy.microsoft.io/npm/   # or your usual registry
npx playwright install chromium
```

### Capture order

Shot ids follow the tour order (Standard harness, then Both harnesses, then the Microsoft Copilot harness; categories and levels within each). Capture one harness at a time so you stay in one experience:

```powershell
cd tools/screenshot-capture
node capture.js --features --list                         # what exists and what is missing
node capture.js --features --harness=standard --missing   # 1. Standard harness
node capture.js --features --harness=both --missing       # 2. Features that span both
node capture.js --features --harness=microsoft-copilot --missing   # 3. Microsoft Copilot harness
```

Useful variants:

```powershell
node capture.js --features --feature=mc-skills,topics     # only these features
node capture.js --features --only=85                      # one shot id
node capture.js --features --dry-run --feature=mc-skills  # print the plan, no browser
node capture.js --features --all --feature=topics         # re-capture existing shots
```

The ids shift when the catalog changes, so prefer `--feature=` for repeat work. npm 11 drops unknown flags from `npm run ... -- --flag`, so pass flags to `node capture.js` directly. `npm run capture:features` is a shortcut for `node capture.js --features`.

### What happens for each shot

1. The tool opens Chromium and, where the shot has a `navSection` (topics, settings), jumps to that page of the agent you opened. Otherwise it prints where to go.
2. It prints the steps to reach the screen, what the screenshot must show, and the numbered callouts it will look for.
3. You set up the screen, then press **Space** to snap, **r** to retry, **n** to skip, **q** to quit.
4. It saves `docs/feature-tour/screenshots/<filename>` and a `<name>.callouts.json` next to it with the position of each callout (fractions of the viewport). Callouts whose text was not visible are reported; reveal them and press **r**, or accept that they appear in the list only.

Capture at the default 1440 by 900 viewport. Do not include real customer data, tenant names, user names, or secrets in a screenshot.

### After capturing

```powershell
npm run feature-tour:verify    # lists what is still pending; fails on invalid files or sidecars
npm run feature-tour:build
npm run feature-tour:serve     # check the pages and the tour in a browser
git add docs/feature-tour/screenshots
```

Commit and push. The workflow rebuilds the site; captured shots replace their placeholders and the callouts become hotspots, with no code changes. `node tools/screenshot-capture/verify-shots.js --strict-missing` makes pending screenshots a failure if you want a hard gate once everything is captured.

If a callout lands on the wrong element, add a `shotOverrides` entry with a more specific `text`, then re-capture that shot.

## Add a feature

1. Add the feature to `portal/lib/lab-builder/features.json` following [Lab builder: extending the catalog](lab-builder.md) (harness, level, steps, Learn URLs, `lastVerified`).
2. Run `npm run feature-tour:build`. The feature appears on the overview, in the tour, and in the shot list.
3. Optional: add curated shots to `overlay.json` for a better capture plan.
4. Commit the catalog change and the regenerated `feature-shots.json`.

## Tests and checks

| Command | What it checks |
| --- | --- |
| `npm run feature-tour:test` | Every feature appears exactly once; harness, level, and availability match; Learn links are well formed; no earlier harness name or British spelling; placeholder versus captured detection; shot list schema, unique filenames, and callouts; the committed shot list is current; accessibility basics and WCAG AA color contrast. |
| `npm run feature-tour:check` | The committed shot list matches the catalog and overlay. |
| `npm run feature-tour:verify` | Captured and pending screenshots, invalid images, orphan files. |

The same checks run in the **Validate content and tooling** workflow.

## Terminology

Use "Microsoft Copilot harness" everywhere. Some Learn pages and URLs still use an earlier name, so you may see it in a link; do not copy it into site text.
