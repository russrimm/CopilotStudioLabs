# Dynamic Microsoft Training and Lab Generator — Screenshot Capture Tool

Interactive Playwright script that helps you capture every screenshot referenced in a lab's `index.md`, with the exact filenames already wired into the markdown.

## What it does

1. Launches headed Chromium so you can sign in normally, then persists auth in `./.auth`.
2. Walks [`shots.json`](./shots.json) one shot at a time, printing the section and setup steps.
3. Optionally navigates, sets viewport/zoom, and best-effort dismisses cookie banners, teaching tips, popovers, and toasts before prompting.
4. Waits for your keystroke, captures the active tab, saves to `labs/<lab>/assets/<filename>.png`, and verifies the PNG.

The script never types into Copilot Studio or configures the agent — you drive sign-in, UI setup, and final shot approval.

## Local Capture Companion (capture from the portal)

The Azure-hosted portal has no browser and no way to sign in to your tenant, so it cannot capture screenshots itself. The **Local Capture Companion** (`companion.mjs`) runs on your own computer instead: the portal queues a capture job, the companion steps through each shot in a visible browser window (Microsoft Edge, Google Chrome, or the Chromium that Playwright installs: on a PC with a Windows work account it tries Chrome and Chromium first, so a screenshot never silently comes from your work account; see [Which account the screenshots come from](#which-account-the-screenshots-come-from)), checks every image, hides account details, and uploads it back. The portal verifies the image again, then updates the lab's HTML, Word, and PowerPoint files and its Microsoft Learn sync state automatically. Paste or upload in the portal is the fallback for any single shot.

### Quick start

1. In the portal, open **Settings > Configuration > Setup checklist** and select **Connect your computer** on the **Screenshot computer** row (a lab's Screenshot Center has the same button). Download the companion from the pairing card (or use this folder from the repository). You need Node.js 20 or later.
2. Unzip it, then start the companion with a launcher. The launchers are in the `capture-companion/tools/screenshot-capture` folder of the download (or `tools/screenshot-capture` in the repository), next to this file: `start-companion.cmd` (Windows), `start-companion.ps1` (Windows PowerShell), and `start-companion.sh` (macOS and Linux). Double-click `start-companion.cmd` on Windows, or run it from a terminal. A launcher installs what is missing the first time (`npm install` and `npx playwright install chromium`).

   Run this from the folder where you unzipped the companion (the folder that holds `capture-companion`). The portal shows the same command with your pairing code filled in, ready to copy:

   ```powershell
   .\capture-companion\tools\screenshot-capture\start-companion.cmd --portal=https://<your-portal> --code=ABCD-EFGH     # Windows PowerShell or Command Prompt
   ```

   ```bash
   ./capture-companion/tools/screenshot-capture/start-companion.sh --portal=https://<your-portal> --code=ABCD-EFGH     # macOS and Linux
   ```

   **Run it from anywhere.** Use the launcher's full path. If you type the folder you unzipped into on the portal's pairing card (**Where did you unzip the companion?**), it shows the full path for you. The folder stays in your browser and is never sent to the portal. A path with spaces, such as a OneDrive folder, needs quotes. In Windows PowerShell, start with `&` and use single quotes; in Command Prompt, use double quotes without the `&`; in macOS and Linux shells, use single quotes:

   ```powershell
   & 'C:\Users\you\OneDrive - Contoso\Downloads\copilot-studio-labs-capture-companion\capture-companion\tools\screenshot-capture\start-companion.cmd' --portal=https://<your-portal> --code=ABCD-EFGH
   ```

   ```bash
   '/Users/you/My Files/copilot-studio-labs-capture-companion/capture-companion/tools/screenshot-capture/start-companion.sh' --portal=https://<your-portal> --code=ABCD-EFGH
   ```

   **Next time you only need the launcher.** The pairing is remembered, so no `--portal` or `--code` is needed. Every time the companion starts it prints `Next time, start it from any folder with: ...` with the launcher's full path, quoted for your shell (never the pairing code), so you can copy it from there. Started with `node companion.mjs` directly, it prints the `node` form instead. The line stays on your computer: the path is never sent to the portal.

   **Keep the code folder and the data folder apart.** The unzipped folder holds only the companion's code. Your pairing and browser sign-in live in a separate local folder of your user account (on Windows, `%LOCALAPPDATA%\CopilotStudioLabsCompanion`), so unzipping, moving, or deleting the code folder, even inside OneDrive, never loses or syncs your sign-in.

   Or, from the repository: `cd tools/screenshot-capture && npm install && npx playwright install chromium && npm run companion -- --portal=<address> --code=<code>`. Without `--portal` and `--code` it asks for them. The pairing code works once and expires in 10 minutes.
3. Leave the window open. The portal shows **Companion connected** (and the **Screenshot computer** row of the Setup checklist turns to Ready). Queue a capture there for a lab or for the shared library; the companion picks it up within a few seconds.

   A picture the companion captures for a lab (account details hidden, every check passed) is also added to the shared library when it is a shared slot, so the next lab reuses it instead of retaking it. The companion itself does not change: the portal decides, from the verification record, and never replaces a library picture that a person marked accurate. See [Capture once, reuse everywhere](../../docs/lab-builder.md#capture-once-reuse-everywhere).
4. The first time a product needs sign-in, the browser window shows the Microsoft sign-in page and the companion says **Waiting for you to sign in to <product>**. Sign in yourself, and when it asks **Stay signed in?** choose **Yes** so the sign-in lasts. The companion remembers it on this computer, so you sign in once per product, not once per screenshot. See [Signing in](#signing-in-once-per-product) for what is saved and how to start over.

### Where to capture, and how each screenshot is taken

A capture needs to know *where* to look in your tenant. Before this release every shot opened the product's generic start page, so agent screens (Overview, Instructions, Knowledge, Settings, Test pane, Publish) could not be reached and the companion photographed whatever page was open. Now each product has a small **Capture settings** model, saved with the active brand profile and overridable per lab (Screenshot Center > **Capture settings**, or the inline prompt that appears when shots are waiting for an address):

| Product | What it needs | Setting |
| --- | --- | --- |
| Copilot Studio | The agent. Optional: the environment (the sign-in redirect finds your default one) | **Agent address** (open the agent and copy the address bar) or **agent name** (opened from the Agents list by its exact name); optional **environment address** |
| Agent Builder | The agent's name | **Agent Builder agent name** |
| SharePoint | The site | **SharePoint site address** (a lab built with a site fills this in by itself) |
| Power Platform | The environment | **Power Platform environment address** |
| Microsoft Foundry | The project | **Foundry project address** |
| Admin centers | Optional | **SharePoint admin** / **Microsoft 365 admin** addresses |

Addresses must be `https`; names are at most 80 characters. They travel to the companion as `CAPTURE_*` variables (addresses) and job settings (names). The portal shows only their *names* in a job, never the values, and the trace never records them.

Every shot is classified honestly into one of three modes, and each shot card shows its mode and why:

- **Automatic** (`auto`): the screen can be reached by its address and read-only navigation, so the computer does it. With the agent known it goes **straight to the screen** (for example the agent's `/settings` page), brings a labeled tab into view only if the lab points at one (a read-only click on a navigation item or tab, matched by its *exact* name), waits until the page is really ready, and takes the picture. If the address does not land on the screen it falls back to the product's own navigation. If a required step cannot be done it **stops with the reason** (for example `Could not find “Generative AI” on the agent's Settings page`) instead of photographing whatever is open.
- **Guided** (`guided`): the screen needs something the computer should not create: an open dialog, a test conversation, a publish confirmation, a result, the details of one tool. The companion opens the closest page and shows a small toolbar on the page with plain instructions and three buttons: **Capture this screen** (shortcut **Alt+Shift+C**), **Skip** (**Alt+Shift+X**), and **Stop**. You set the screen up and capture it; the companion removes the toolbar from the page before the picture, verifies, and uploads as usual. The toolbar shows only the instruction text: it never reads the page, never touches an input, and is never in the picture.
- **Manual** (`manual`): outside the browser (a terminal, Visual Studio Code). Capture it with an OS screenshot tool and upload it.

A capture job runs in one of four **modes**, chosen in the Screenshot Center: **Automatic (recommended)** (`autonomous`: the computer sets up every browser-reachable screen itself, see [Automatic capture](#automatic-capture-autonomous-mode)), **Automatic, read-only** (the same, but it never creates anything), and under **Advanced** **I will set up each screen** (`guided`), **Smart** (`smart`: automatic shots run first and unattended, then guided shots wait for you), and **Only what needs no setup** (`auto`: guided shots are marked *needs you*). Unattended use is safe: a guided shot waits for you at most `--guided-wait` seconds (default 120); if nobody answers, that shot and the other guided shots in the job are marked **needs you**, so a companion left running in `--watch` mode never hangs on a screen nobody is there to set up. With `--headless` guided shots are marked *needs you* at once.

**What each outcome means and how to fix it.** The Screenshot Center groups the shots that did not end well by cause, with one fix per group:

| Group | What happened | Fix |
| --- | --- | --- |
| No agent address set (or SharePoint site, or another address) | The shot needs your tenant address, so it was held back. Nothing was opened | Add it in **Capture settings**, then retake. For an agent, this appears only when you chose **An agent I choose** or the practice agent could not be created; the default **The agent created earlier in this capture** needs no address |
| Waiting for the agent | The shot should use the practice agent created in this capture, but it could not be created or opened (the account cannot create agents here, this computer has not agreed to create one, or the agent was made under a different sign-in). The reason is in the shot's note | Fix what the note says and select **Retry**, or choose **An agent I choose** and add your own agent's address |
| The agent was not found | The agent name matches no agent in the environment | Check the name (it must match exactly) or use the agent address |
| Sign-in needed | The product asked for a sign-in | Sign in in the companion window, then retake |
| The wrong screen was open | The address or navigation ended on a different page. The picture is kept for review: *This is the Copilot Studio home page, not the agent's Settings page* | **Retake guided**, or check the agent address |
| A control could not be found | A required step (a tab the lab points at) is not on the screen | **Retake guided** and open it yourself |
| The page did not finish loading | The picture was blank or almost one color, even after waiting longer | Retake; check the page opens in the companion's browser |
| Paused: the browser window was closed | You closed the window (or pressed **Stop**). The remaining shots are *paused*, with one message, not failed | **Resume** (it queues exactly those shots) |
| This screen needs you | A guided shot in automatic mode, or nobody was there | **Retake guided** |

**How a picture is checked now.** The page address is the main signal: when the plan knows the screen it expects (for example the agent's Overview page), a picture whose address is a different page is *never* accepted automatically; it goes to **needs review** with a sentence that says what was captured and what was expected. When the address matches, the expected labels are only a soft hint, so a correct picture is not stuck because a label from the lab text never appears. Labels are cleaned first (typos such as *Start building form scratch* are corrected, stop words, placeholders, and sentences are dropped) and matched without caring about case, punctuation, plurals, or a one-letter typo. Blank pages, sign-in pages, and almost-one-color pictures are still rejected, and the magic-byte, size, and filename checks are unchanged. A picture you set up in guided mode only has to be in the product. The portal judges every upload against the plan's own expectation, never against what the companion says.

**Waiting for the page.** Before every picture the companion waits for all of these: the page has loaded, no loading indicator is visible (`aria-busy`, `role=progressbar`, skeleton or spinner classes), the page has stopped changing for a quiet window, and two pictures in a row are identical. A picture that still comes out empty is retried once with a longer wait. The budget is `--ready-wait=<seconds>` (default 20), and what was waited for is in the trace.

**The newer agent layout.** A newer Copilot Studio agent shows a tab strip (Build, Preview, Evaluate, Monitor) instead of separate Knowledge, Topics, Tools, and Settings pages. Measured on a real agent: an address such as `.../knowledge` stays in the address bar but the page shows the Build tab, so a picture could pass the address check while showing the wrong screen. After the page settles, the companion looks for that tab strip (control roles and names only, never page text). If it is there, the Evaluation screen opens the Evaluate tab, the Analytics screen opens Monitor, and Overview stays on Build. A screen that has no page of its own there (Knowledge, Topics, Tools, Channels, Settings) is not photographed as Build: it stops with *This agent uses the newer Copilot Studio layout... which has no separate Knowledge page* (a screen whose steps could not be done says the same before its own reason). Use **Retake guided**, or **Show me once** so the computer learns the screen in that layout. Agents in the classic layout are unaffected.

**If the browser misbehaves.** An interrupted navigation (`net::ERR_ABORTED`, a timeout, a reset connection) is retried twice with a growing pause. A crashed tab is replaced by a new tab in the same browser and the shot is tried again. Closing the browser window pauses the job once and tells you how many shots are waiting; in `--watch` mode the companion keeps running and picks up the next job, for example the one **Resume** queues.

**What it never does.** In every mode the companion never signs in or out, switches or removes an account, deletes or removes anything, changes tenant, environment, admin, billing, licensing, security, DLP, or permission settings, installs or consents to an app, creates a connection with credentials, shares or publishes to anyone else, sends a message or an email, or uploads or downloads your files. In read-only and the older modes it also never creates, edits, saves, or publishes anything: it refuses any control named Publish, Create, Save, Submit, Send, Add, Edit, New, Deploy, Apply, Confirm, Run, and similar (and any control that submits a form), whatever the plan says. Automatic mode adds only the interactive-safe actions listed in the tier table below.

**Older portals.** The companion still runs a plan from a portal that does not classify its shots (the way it did before, with the stricter control rules). Download it again after the portal is updated to get the new behavior.

### Automatic capture (autonomous mode)

Automatic mode is for "do it for me": the computer sets up the screen itself (opens the test pane and asks a sample question, opens a dialog and cancels it after the picture, opens an item's detail panel, opens the Agents menu and New agent in Microsoft 365 Copilot to reach the Agent Builder start screen) and photographs it, with no click from you after the one-time sign-in. **Capture all screenshots automatically** in the Screenshot Center queues it (`options.mode: "autonomous"`), and the Step 8 capture-on-build checkbox uses it when a computer is connected. Guided capture stays as a last resort for a shot that automation tried and could not complete, and the portal says exactly which step failed.

**Consent first.** The first automatic job shows a consent card in the Screenshot Center. The portal sends the computer only what you allowed; a job without consent fields behaves as read-only, and the companion enforces what the job carries.

**The safety tiers** (one table, in `guard.mjs`, shared with the portal and shown in the consent card; `node companion.mjs --dry-run-plan` prints a job's steps by tier without a browser):

| Tier | Name | Examples | When |
| --- | --- | --- | --- |
| 0 | Look | Navigate, open sections, expand, select tabs, scroll, hover | Always |
| 1 | Try | Open menus, dialogs, panels, and pickers; type into the test chat and send test messages; type into search and filter boxes; fill a dialog's fields **without confirming** it, then cancel it after the picture; discard unsaved edits | Automatic mode with consent. Never confirms a committing or destructive button |
| 2 | Practice | Create, edit, save, and publish **only inside a practice agent the companion created itself** (named `Classic shots - ...` or `Copilot shots - ...`; before 1.8.0 `Lab screenshots - ...`; listed in `.practice-agents.json`), only for shots that really need that state; only the default internal publish | The consent option *and* this computer's own yes (asked once in the console, or `--allow-practice-writes`; saved until `--no-practice-writes`). Otherwise the shot is captured as far as Tier 1 allows and labeled *needs practice agent*. [Build the agent from scratch](#build-the-agent-from-scratch) is this tier for a whole lab |
| 3 | Never | Sign out; switch, add, or remove accounts; delete or remove anything (cleanup included); change tenant, environment, admin, billing, licensing, security, DLP, or permissions; install or consent to apps; create connections with credentials; touch anything but the practice agent; send messages or emails; upload or download files; share or publish to external channels; leave the product's own sites | Never |

Every click and every typed character goes through one gate that classifies the control (its role, accessible name, the nearest dialog's title, its ancestors) before acting, refuses unknown controls in Tier 2 and 3 contexts, and records the decision in the trace. A neutral button in a dialog titled *Delete agent* is treated as destructive. Words such as Delete, Remove, Sign out, Publish to channel, Share, and Invite are recognized in several languages, with any capitalization, and by their icon-only accessible names. After a run, `practice-report.md` (next to the companion's data) lists everything it created, and the portal names it; **the companion never deletes anything**, so you delete the practice agent yourself.

**A resilient executor.** Each setup step is a small verified state machine. A control is found by ranked strategies (role and exact name inside the expected area, role and a normalized name, `aria-label` or `title`, the visible text's nearest interactive ancestor, then a fuzzy match over interactive controls only), across iframes and open shadow DOM. **The ranking depends on what a wrong click costs (companion 1.8.3).** A step that creates or confirms, or any tier 2 write, finds its control by its **exact name only** (role and name, or `aria-label`, `title`, placeholder, or test id): no partial name, no visible-text match, no fuzzy match. A step that opens a menu or a dialog that the next step works in uses the exact name and the name's words as whole words in order, and never the visible-text or fuzzy strategies. Typing goes only to a box whose own name matches. Only navigation (open a page, select a tab, open an item) may fall back to the looser strategies, and then only to a control of the role the step names (a plain button called *Settings* is not the *Settings* menu item). This rule exists because a fuzzy match once clicked the lower left **More options** button for **More create options** (a name score of 0.77) and the step reported success. A control that is not on the page yet is **waited for, never replaced**: every step waits for its control for `findMs` (7 seconds by default; the practice agent's **More create options** step waits up to 60, because a real Agents list draws its controls 15 to 30 seconds after navigation). A step that opens a menu or a dialog can name the items the opened menu must list (`expect.menuItems`): it passes only when the menu that opened lists them, and a different dialog that opened instead (the account flyout, for example) is closed with Escape and named in the failure sentence. Nothing inside a dialog named *Account* or *Profile*, and no control named like the account menu or sign out, is ever clicked. A click that changes nothing is not success: it tries the next candidate or strategy. A step passes only when its expected evidence is on the page (a dialog, a label, an address, a finished answer: no typing indicator and a stable answer area). Cookie banners, teaching and what's-new pop-ups, toasts, and leave-the-page prompts are dismissed. When a shot cannot be completed it ends *needs you* with the exact failing step and writes a redacted **diagnostic bundle** to `.captures/diagnostics/` (roles and accessible names of the visible controls around the failing step, the URL host and path, the step id, strategy attempts, and timings; no query strings, cookies, page text, or account or tenant names). Send that file if you ask for help. `node companion.mjs --diagnose[=<product>]` writes one for the page open in a live browser.

**Show me once.** When automation cannot complete a shot, press **Show me once** on that shot and set the screen up by hand. The companion records the interactions as tier-checked declarative steps (role, accessible name, and area; never coordinates, never typed values that look like secrets, never account information; Tier 3 interactions are skipped) and saves the recipe under `.recipes/` on this computer. The next run replays it automatically with the same self-healing, and a replay that fails marks the recipe stale. **Share this recipe** is your explicit choice: the portal validates it again (it rejects URLs with query strings, email addresses, tenant or environment GUIDs, and long text) and offers it to every lab and user.

**Background.** `--background` (the portal's **Run in the background when already signed in**) uses a hidden window with the saved session. If the tenant refuses it (Conditional Access, a sign-in redirect), the companion opens a normal window with one message. The first sign-in is always visible. `--headless` still cannot sign in.

**What is verified and what is not.** Automatic mode is proven against the deterministic pretend product site in `test/fixtures/fake-product-site.mjs` (streaming test pane, dialogs that must be canceled, a publish dialog, create-agent, Delete agent, Sign out, an admin page, iframes, shadow DOM, a cookie banner, a leave-page prompt, renamed controls, a flaky control, an older Agent Builder page with no direct address, a SharePoint site) in real Chromium and the installed Edge: `node test/fixtures/autonomous-matrix.mjs` prints the before and after numbers. Microsoft 365 Copilot Agent Builder has its own pretend site shaped like the real pages read on 2026-11-27 (`test/fixtures/fake-m365-copilot-site.mjs`; the Agents button opens an Agents menu dialog with a New agent link to the start screen), and only the start screen has a recipe: the other Agent Builder slots end as *Needs you* with their own reason ([docs/m365-agent-builder-capture-slots.md](../../docs/m365-agent-builder-capture-slots.md)). **Real SharePoint pages and the Agent Builder screens after the start screen are not verified, and the Standard (Classic) experience is verified on a real tenant only for the switch, the new tab, the Agents list, and the agent page's tab strip (read only, 2026-11-24), not for creating a Standard agent or for a full capture; the newer Copilot Studio layout was verified on a demo tenant for the steps listed under *Build the agent from scratch*.** The control names, landmarks, test-pane markup, and timings of the unverified pages are assumptions until a run on a real tenant. When a built-in step does not match a real page the shot ends *needs you* with a diagnostic bundle, and **Show me once** teaches the companion the real step.

### What the companion proves, and when it stops (companion 1.7.0)

A picture that shows the wrong screen used to be accepted as long as the address was on the right product. From 1.7.0 the companion captures a screen only when it can show it is the screen the lab describes, and the portal checks the evidence again (it never trusts the companion):

- **It stops on a public page.** Before a picture it reads the page's own signals (`readPageSignals` in `redact.mjs`): a visible **Sign in** control near the top with no account control. When both are true it does not photograph anything. The shot, and the product's remaining shots, end with *You are not signed in to <product>. Sign in once in the companion window, then retake the shot.* (the same pause as a sign-in page).
- **It never photographs "whatever is open".** When no recipe, address, or step reaches the expected screen (another product's screen, or a Copilot Studio screen the recipes do not know), the shot becomes a person shot with the portal's fixed reason (for example *Needs another Microsoft product*) and an error that ends *Use “Retake guided”, or upload the picture.* Nothing is photographed. A shot whose address itself opens the screen is not affected.
- **It sends evidence version 2.** The upload says what the page showed: the final address (ids zeroed), the visible labels, the sign-in and account signals, and what masking found and covered (`controls`, `lists`, `listsMasked`). The portal needs an expected label (or an address that names a screen of its own, or something the computer chose inside the page and the page then showed) before it accepts a picture on its own; otherwise it is **Needs review**.
- **It hides more.** Greetings (`Welcome, <name>!`, `Hello, <name>`, `Hi, <name>`, `Good morning, <name>`), account chips (`Work <name>`, `Personal <name>`), initials avatars, plan or license chips (`M365 Copilot (Premium)`), the environment name (`<name> (default)`), email addresses, and lists of your own items (Recent, Your recent, Last opened, Pinned, Chat history: the item text is covered and the layout stays).

What it cannot do: it does not read a picture's text (no OCR), and it cannot tell that a screen is a *similar* page of the product. The portal also compares each new picture with the others (identical or near-identical pictures under different slots need review). See [Pictures that show the wrong screen](../../docs/lab-builder.md#pictures-that-show-the-wrong-screen), which also describes the read-only audit (`node tools/lab-builder/audit-screenshots.mjs --out=<folder>`) and the tool that moves pictures that look wrong to the kept pictures list (`node tools/lab-builder/quarantine-screenshots.mjs --dry-run`). An older companion keeps working, but the portal says *Update your Local Capture Companion. Older versions cannot prove the screen, so their pictures are saved for review.* and saves everything it captures for review.

### Harnesses: Standard (Classic) and Microsoft Copilot (companion 1.8.0, corrected in 1.8.1)

Copilot Studio has more than one harness, and a picture of one must never be passed off as a picture of another. Every Copilot Studio shot in a plan says which harness it needs (`shot.harness`: `standard`, `microsoft-copilot`, `customer-conversation`, or `either` for a screen outside the agent; any other product has none), and the label is shown wherever a picture is identified (**Standard (Classic) harness**, **Microsoft Copilot harness**, **Customer Conversation harness (preview)**). A new agent is a **Microsoft Copilot harness** agent by default (the Build, Preview, Evaluate, and Monitor tabs). A **Standard (Classic) harness** agent lives in the classic experience, which opens on its own address, `https://copilotstudio.preview.microsoft.com/` (agent pages at `/environments/<id>/bots/<id>/...`). The companion treats the harness as a requirement it enforces and proves, never as a guess from whatever page opened.

**What the real product does (observed 2026-11-24 on a real tenant, read only, with the owner at the PC; companion 1.8.1 is built on it).** Companion 1.8.0 was written from guesses and was wrong in these ways: (1) `https://copilotstudio.microsoft.com/` opens the environment Home (Home, Agents, Workflows, Apps; Preview) and takes 15 to 30 seconds to draw its controls. (2) The lower left control is a button named **More options**; its menu offers *See what's new, Solutions, Open classic experience, Power Platform Admin Center, Learning resources, Session details* **in every experience** (the default one, the preview address, and a Standard agent page), so the menu says nothing about which experience a page is in. (3) **Open classic experience** shows a feedback prompt (**Skip feedback** is clicked; **Submit** never) and then opens `https://copilotstudio.preview.microsoft.com/environments/<id>/home` **in a new browser tab**; the first tab stays on the default address. (4) That address also opens directly in a new tab with the same sign-in, and opening a Standard agent from the default Agents list redirects, in the same tab, to `.../bots/<id>/overview` on the preview address. (5) The Agents list (the same on both addresses) is a table with Name, Status, Owner, Last modified, and **Agent harness**; each row's harness cell reads *Microsoft Copilot* or *Standard* and has a tooltip appended to the cell text. (6) A **Standard agent page** shows a **tab strip** (Overview, Knowledge, Tools, Agents, Topics, Activity, Evaluation, and an overflow button), not a side navigation; a **Microsoft Copilot agent page** shows the tab strip Build, Preview, Evaluate, Monitor. (7) On the Agents list, **More create options** offers *Agent, uses Copilot Credits* (Microsoft Copilot), *Customer conversation agent, uses Copilot Credits*, and *Agent, Standard*.

**Standard (Classic) pictures.** Before the screen is opened the companion switches to the classic experience, exactly as you do by hand: **the ellipsis in the lower left corner (the button named More options), Open classic experience, then Skip feedback**. The plan, the dry run, and the status lines print it as `Switch: ellipsis in the lower left corner > Open classic experience > Skip feedback.` The feedback prompt does not always appear; when it does, **Skip feedback is the only button ever clicked** (never Submit or Send feedback). A prompt that has only Submit stops the shot as *needs you*, and nothing is submitted. **The click opens the classic experience in a new browser tab on copilotstudio.preview.microsoft.com, and the companion follows it**: it finds the page that opened (or accepts the same tab), waits until it is on the preview address and drawn (up to 45 seconds for the menu, 30 more for the new tab), brings it to the front, **closes the first tab (the default address) so that exactly one tab stays open** (from 1.8.2, so a person watching sees only the Standard page), and takes the rest of the shot on that page. The pages of the shot (Agents list, agent pages) stay on the preview address, where a Standard agent opens at `/bots/<id>/...`. If the click path does not produce a classic page, the preview address is opened directly in a new tab as a recovery, and the proof records which way was used (`via`: `click-path` or `preview-address`); if neither works, the shot stops as *needs you* with a plain reason. The single classic tab is kept for the Standard pictures that follow and is **taken back to the default address, and proven again, before the first Microsoft Copilot picture** (still one tab). The landmarks are **read again before every Standard picture**. A Standard practice agent is made with **More create options > Agent, Standard** on the Agents list of the classic tab, after the switch (see [Build the agent from scratch](#build-the-agent-from-scratch)); that menu is offered on both addresses, and making the agent there means it already sits where Standard agents open.

**Microsoft Copilot pictures.** No switch. The companion works in the default experience at `https://copilotstudio.microsoft.com/` with an agent whose **Agent harness** cell says *Microsoft Copilot*. A classic page is never left open next to it: the single tab goes back to the default address (the address is opened again in that same tab) and is proven again. A page that is itself in the classic experience goes back to the default address the same way. When it cannot get back, the shot stops as *needs you*, and nothing in the classic experience is clicked to fix it. The shots of one capture are taken one harness at a time, in the order the plan gives them (a lab built for both harnesses has all the shots of one harness, then all of the other), so the experience changes once: the switch is made once before the first Standard shot, the landmarks are proved before every shot, and the default experience is used again (in the same single tab) before the first Microsoft Copilot shot that follows. A plan that interleaves the harnesses is grouped by the order each harness first appears; each shot still switches or goes back as its own harness needs, and a practice agent is made per harness inside the same capture.

**The proof, before the picture.** The companion reads control names only (never page text), by accessible name (a name that the page doubles in its text, such as `OverviewOverview`, counts once). A **Standard (Classic)** agent page is proven by a **tab strip** with Overview and at least two of Knowledge, Tools, Topics, Agents, Activity, or Evaluation, and none of Build, Preview, Evaluate, and Monitor (an older classic build's side navigation with Overview plus Knowledge, Tools, Topics, Analytics, or Channels is still read as a fallback). A **Microsoft Copilot** agent page is proven by the Build, Preview, Evaluate, and Monitor tabs; Customer Conversation adds Deploy. The address shape (`/bots/<id>/` for Standard, `/agents/<id>` for Microsoft Copilot) and the host are corroboration only, never the proof. The picture is taken only when what it read is the harness the shot needs, and the upload carries what was *proven* (`evidence.harness`: the harness, the landmarks it saw, whether the companion switched, the address host, and how the classic page was reached), never what was assumed. In the log: `Proved the Standard (Classic) harness: Overview, Knowledge, Tools, Topics`. A page in the wrong harness ends the shot as *needs you* with one plain sentence, and nothing is saved: *This agent is Standard; this picture needs the Microsoft Copilot harness. Choose a Microsoft Copilot agent, or let the computer create one.* **Agent selection reads the Agents list first**: the **Agent harness** column (the cell text starts with *Microsoft Copilot* or *Standard*; the older **Powered by** column is the fallback) of the row of the named agent, or of an agent you chose, decides before anything is opened, and a wrong-harness agent is refused the same way. A Standard agent is opened with its row's **Open <name>** button (the product redirects to the preview address), a Microsoft Copilot agent on the default address. **A screen outside any agent (Home, the Agents list) cannot be proven by what it shows**: the Open classic experience menu item is offered in every experience, so it proves nothing, and the 1.8.0 menu proof is removed (a 1.8.0 picture that carries it is treated as unproven and goes to review). The rule is: such a screen is taken in the experience that matches the lab's harness (Standard on the preview address after the switch, Microsoft Copilot on the default address), the page address host is checked and can only *refuse* (a Standard picture on the default host, or a Microsoft Copilot picture on the preview host, is not taken), and the picture is stamped with the host and how the page was reached (`evidence.harnessReached`, `proven: false`) so the portal saves it **for review**: a person accepts it, it is never silently good. **Not verified on a real tenant:** whether the tab strip's tabs have a clean accessible name (the doubled-name case is handled), and a proof for Home and the Agents list beyond the host. **Retake guided** and **Show me once** do not click anything at capture time: the companion reads the landmarks, refuses a wrong harness the same way, and stamps the harness it proved (a page it cannot read, such as a page that is not an agent, is saved without a harness, and the portal sends the picture to review).

**One practice agent per harness.** The computer builds a Classic agent for Standard (Classic) pictures and a Microsoft Copilot agent for Microsoft Copilot pictures, never one for the other. The names carry a short marker and fit the 30 characters the product keeps: `Classic shots - <short lab title>` and `Copilot shots - <short lab title>`. Each agent is proven by its landmarks before it is used and is recorded in `.practice-agents.json` under the harness it was proven to be in. An agent recorded before harnesses were recorded (`Lab screenshots - ...`) is listed as *Harness not recorded* and is never reused for a harness-specific picture; a new one is built and the log says so. The computer does not build Customer Conversation agents (a plain reason; **Retake guided** still works, with the same landmark check). *The agent created earlier in this capture* resolves to the agent of each slot's harness, and *An agent I choose* is refused for a slot of another harness.

**A lab and its harness.** A lab built for one harness takes only that harness's pictures for every Copilot Studio slot. A module that is not written for the lab's harness arrives with `shot.harnessGap` and is stopped as *needs you* (*This module is written for the Microsoft Copilot harness, but this lab is built for the Standard (Classic) harness, so its picture cannot be taken in the lab's harness.*); the other harness is never tried.

**Standard (Classic) recipes (companion 1.8.2; the page was read on a real tenant on 2026-11-26, read only).** The Standard agent page has a tab strip (Overview, Knowledge, Tools, Agents, Topics, and a control named *N more options*; at 1440 pixels or wider Activity and Evaluation are tabs of their own, and narrower, Activity, Evaluation, Monitor, and Channels are all in the overflow menu), a top bar (**Search your agent**, **Publish**, **Settings**, **Options**, **Test**), and the Test panel on the right of every tab. Every recipe that opens a tab selects it by name and, for Activity, Evaluation, Monitor, and Channels, opens the overflow menu when the tab is not on the strip. **Set the instructions** was the step that failed in every earlier run: the Instructions card has an **Edit Instructions** button that opens an inline editor (a text box named *Describe what you want this agent to do, its tone, and rules*, with **Cancel** and **Save**; **Save** stays disabled until the text changes). The recipe now selects **Edit Instructions** (unless **Cancel** and **Save** are both already there), checks the editor really opened, types into that text box only (scoped to the Instructions card, never the Test panel's text box, with no fuzzy fallback to another box; an agent that already has instructions gets the whole text replaced), reads the text back, checks **Save** is enabled, saves, and checks **Save** is disabled again (or the editor closed and **Edit Instructions** is back). **Companion 1.8.4:** a real run showed that the text box with that name is also on the page while the editor is closed (it does not take text), so the box never counts as an open editor any more: only **Cancel** and **Save** together do. If the text equals what the agent already has, **Save** never enables; that is a success (*the instructions already match, nothing to save*) and the editor is closed with **Cancel**. A missing button says *the Edit Instructions button was not found*, and an editor that did not open says *Edit Instructions was clicked but the editor did not open: Save and Cancel are not on the page*. A disabled target is reported as its own cause (*Save is disabled: the text did not register in the Instructions editor*), and a step that cancels answers the unsaved-changes dialog (**Close**, **Discard**, **Cancel**) with **Discard**. The diagnostic file names the text box that received the text (`typedInto`). After the switch the first tab is closed so exactly one tab stays open, and one plain line is logged before each picture: *Taking this picture in the Standard (Classic) harness: copilotstudio.preview.microsoft.com, agent <practice agent name>, proof: <landmarks>*. A Standard lab's Create an agent picture is the Agents list with the **More create options** menu open and **Agent, Standard** in view (nothing is chosen). Screens that were never read on a Standard agent (the Add knowledge and Add a tool dialogs, the new evaluation form, Monitor sessions, most Settings controls, the Test panel's **More** menu, and the Publish dialog) end as *Needs you* with their own reason and are not guessed. Proofs from companion 1.8.1 stay valid (the proof of an agent page did not change). The slot-by-slot table and the read-only checks that would settle the rest are in [docs/standard-capture-slots.md](../../docs/standard-capture-slots.md); the review rules for a picture taken in the wrong harness are in [Wrong-harness pictures](../../docs/lab-builder.md#wrong-harness-pictures-how-a-picture-is-judged). Tests: `test/standard-page-browser.test.mjs` (real Chromium against the `realStandard` page of the pretend site) and `test/standard-harness.test.mjs`.

**Command line and files.** In the shared library a harness-specific picture is saved under a name that carries its harness: `agent-overview.classic.png`, `agent-overview.copilot.png`, `agent-overview.customer.png`. `node capture.js --product=copilot-studio --harness=<standard|microsoft-copilot|customer-conversation|either|both>` filters the feature tour list; a slot marked `both` is kept once per harness and is captured only with `--harness=standard` or `--harness=microsoft-copilot` (otherwise it is skipped with a plain line). `--list`, `--dry-run`, `status.mjs`, and the interactive capture print each shot's harness, its switch step, and its proof, and the interactive tool refuses a snap when the agent page is definitely in another harness. Tests: `test/harness-run.test.mjs` (no browser), `test/harness-browser.test.mjs` and `test/harness-practice-browser.test.mjs` (real Chromium against `harnessMode` of the pretend site).

### Build the agent from scratch

Most lab shots show an agent. By default **the computer builds a new practice agent itself** in your demo account, by following the lab, and takes each screenshot as the lab reaches that state. You do not need an agent, and you do not click anything after the one-time sign-in. This is the default path of **Capture all screenshots automatically**. In the Screenshot Center, the choice **Which agent should these screenshots use?** has two options: **The agent created earlier in this capture (recommended)** (nothing to type) and **An agent I choose** (paste its address or type its name, and the computer only looks at it).

**Which agent every screenshot uses (companion 1.6.2).** The practice agent is created (or reused from this lab's earlier capture) before the first screenshot that needs it, and the companion keeps its address in memory for the rest of the run and in its local record (`.practice-agents.json`, never sent to the portal). Every later shot that shows an agent opens exactly that agent, with no address supplied and no prompt: the plan orders the shots that create the agent first (`capture.agent.creates`), and a shot whose agent comes from the creation step (`capture.agent.via: "created"`) is ready, not waiting for an address. The job carries no other agent's address or name (`options.agentSource: "created"`), so no other agent in the tenant can be opened, and the page-loading guard stays in force (an address that is still loading is never opened again). If the agent cannot be created or opened (the account cannot create agents, this computer has not agreed to practice writes, or the creation step failed), each dependent shot ends **Waiting for the agent** with one plain reason, for example *The practice agent could not be created (...), so this screenshot needs an agent address.*, and is never run on a guessed page. A practice agent is tied to the sign-in that made it, by a random 12-character marker kept next to the browser profile (`companion-account.json`; it says nothing about who signed in): a later job under a different sign-in does not use that agent, creates nothing in its place, and says *The practice agent for this lab was made under a different sign-in and was not used. Sign in with the account that made it, or choose Start fresh to build a new practice agent.* A record from before the marker is tied to the first sign-in that reuses it. A job from an older portal (no `agentSource`) behaves exactly as before; a portal that sees a companion older than 1.6.2 at the practice level says in plain words that it cannot hand the agent over, and keeps the older behavior.

**What you do once.** In the Screenshot Center, leave **The agent created earlier in this capture (recommended)** selected and select **Allow the computer to create it** (or start a capture). A consent card lists exactly what the computer will create and change, and what it will never do; tick the box and select **Allow and build the agent**. The first time a job needs it, the companion also asks you once, in its own console window, to confirm two things: that this computer may build a practice agent (saved per product, see `--no-practice-writes` to take it back), and that the account in the window it just opened is the right one. You sign in once in that same window (only if it asks): you do not sign in twice, and the confirmation is a typed `yes`, never saved with the account's name. `--allow-practice-writes` still works as an advanced alias for the first question.

**How the creation starts (companion 1.8.1; creation verified on a real tenant on 2026-11-26, the form after the choice is not).** On the Agents list the companion opens **More create options** (observed 2026-11-24 to offer *Agent, uses Copilot Credits*, *Customer conversation agent, uses Copilot Credits*, and *Agent, Standard*, on both addresses). A **Standard (Classic)** practice agent starts from **Agent, Standard**, in the classic tab after the switch (the same menu is offered on the default address, so the option itself needs no switch; the companion makes the agent on the preview address so it already sits where Standard agents open). A **Microsoft Copilot** practice agent starts from **Agent, uses Copilot Credits**; only when that menu itself is missing does it fall back to the older **New agent** button. Only these two items are exempt from the rule that refuses any control that spends Copilot Credits, and only for the one create click; **Customer conversation agent** is never clicked. What the product shows after you choose **Agent, Standard** was not read screen by screen, but on 2026-11-26 the recipe created a Standard practice agent this way (named `Classic shots - ...`, recorded as `standard`) and its Overview page was proven Standard, so the creation steps work; what each screen asks is still unlisted, so everything after that click reuses the older recipe steps (name, instructions, save) behind landmark checks: if a step does not match, creation ends as *needs you* with the exact step and nothing further is done. A Standard agent is then found again and opened from the Agents list by its **Agent harness** cell, and its picture is proven by the tab strip. Before this version a Standard agent could only be made after the switch; that was a guess. A shot can also use **An agent I choose** with an existing Standard agent (the tenant already had several), and then nothing is created.

**Creating the practice agent reliably (companion 1.8.3).** Every Microsoft Copilot practice agent failed in a traced run with *the computer could not choose “Agent, uses Copilot Credits” in More create options*. The cause: the Agents list draws its controls 15 to 30 seconds after navigation, the job clicked after about 5, the exact **More create options** button did not exist yet, and the old executor fell back to a fuzzy match and clicked the lower left **More options** button (which opened an *Account* dialog). That step had no expectation, so any click counted as success. Now (1) the **More create options** step finds its button by exact name only and waits up to 60 seconds for it; (2) the step is OK only when the menu that opened lists the harness's option (*Agent, uses Copilot Credits* or *Agent, Standard*), and a different dialog that opened is closed with Escape and named (*a dialog named “Account” opened instead of the menu*); (3) the next step says *the menu was not open* when the menu is gone, never that the option is missing; (4) a Microsoft Copilot agent falls back to the older **New agent** button only when **More create options** was never on the list, and the sentence then names both. **Names are unique within the 30 characters the product keeps**: a practice agent built from a lab is named `<Classic shots - or Copilot shots - ><short lab title> <code>`, where the code is four letters and digits from the lab's key (and from how many earlier agents of that lab *Start fresh* set aside), so two Energy labs no longer share `Classic shots - Energy &`. After **Save** the flow leaves the new-agent page for the agent's own page, and the companion reads the agent's id from that address (waiting up to 20 seconds); only when the page stays on the form does it search the Agents list for the exact name (the row's **Open <name>** button, found by exact name, never a name that merely starts with it, and never the top bar's *Open account menu for <person>*), reading the list again for up to 45 seconds because it can lag. A name that two rows share is never opened. An agent recorded under an older name is still reused by its recorded address. What the Microsoft Copilot creation screen shows after the option is chosen is still **unverified**: the Name field and the Save or Create button that follow are the older steps, and the first one that does not match ends creation as *needs you* with the exact step and a diagnostic bundle of the screen's real controls and dialogs. Tests: `test/harness-practice-browser.test.mjs` (a fake Agents list that draws **More create options** late while the lower left **More options** opens an *Account* dialog with **Sign out**; the old code failed it with the message above), `test/harness-run.test.mjs`, and `test/tiers.test.mjs`.

**What it creates and changes.** One new agent per harness the lab needs, named `Classic shots - <short lab title>` (Standard (Classic)) or `Copilot shots - <short lab title>` (Microsoft Copilot), see *Harnesses* above (before 1.8.0: `Lab screenshots - <short lab title>`; the product keeps at most 30 characters of an agent's name, so the title is shortened at a word: for example `Classic shots - Team`), its instructions and description from the lab's own text, one public Microsoft documentation website as a knowledge source (taken from the lab's Learn links; the SharePoint site you gave is only read), the settings the lab turns on or off (for example Memory), test conversations in the Preview tab (the lab's own sample question, one question outside the agent's scope, and one plain request to ignore its instructions so a picture can show how the agent refuses; nothing from them is saved to the agent, and the activity map or trace is opened beside an answer and closed again), **from 1.6.3 one evaluation test set with one sample question, saved but never run (so it spends no Copilot Credits)**, and publishing only the practice agent, once, to its default (internal) state: the Publish dialog must hold nothing but Add channel and Publish agent (any other control, choice, or warning stops it, and nothing is published), the click is made exactly once and recorded in the local record before it is made, so no later run publishes that agent again. It lists everything it made in `practice-report.md` next to the companion's data and in the portal (names and counts only: no address and no id ever leaves your computer, and the page address sent with a picture has every id replaced by zeros). From 1.6.3 the report also has a *What the screenshot recipes did* section: for each recipe, which shot it took, what it created (or *Created nothing*), and whether it has been seen working on a real tenant yet.

**What it never does.** Everything in the Tier 3 row above, and in particular: delete or remove anything, touch any other agent, share or publish to a channel (Teams, a website, Microsoft 365), invite anyone, change environment, tenant, admin, security, billing, DLP, or permission settings, create a connection that needs credentials or consent, upload or download a file, run an evaluation (a run and a generated data set use Copilot Credits), or leave the product's own sites. The gate is the same one the other modes use, plus three rules that are stricter here: a write is allowed only while the page is inside the practice agent (or the one sanctioned Create flow in the chosen environment), a dialog whose title the computer does not know is never confirmed, and an unexpected prompt of any kind (a license, a consent, MFA, an admin block, a quota or limit message, an error) stops the whole run instead of improvising. Writes are paced, counted against a budget, and a stop request (**Stop** in the portal, Ctrl+C in the console) halts before the next write.

**Where it builds.** In the environment Copilot Studio opens for the signed-in account after sign-in (the default), or the one you name in the consent card (**Where should it build?**, optional). It never clicks the environment picker, and it never uses your Windows work account: the account guard, including the one-time confirmation above, runs before the first write. An account that cannot create agents ends every agent shot with one plain reason, and nothing is changed.

**How the lab is walked.** The shots are ordered by the lab's modules, and each belongs to a stage: create the agent, instructions, knowledge, tools, model, preview (test), evaluate, publish, monitor, and settings. Before a shot, the computer brings the stages it needs into place on the practice agent, once (a stage already done is skipped on later shots and later runs, so nothing is ever created or added twice), proves each step by landmarks (roles, names, the tab strip, the address; never page text), and then puts the screen into the state the picture shows (a dialog open, a question answered). The newer agent layout (Build, Preview, Evaluate, and Monitor tabs) is the main path; the older side-navigation layout is a fallback (the agent is made on its form and screens are looked at; its instruction and knowledge steps are unverified).

**What ends as "needs you", and why.** One plain reason from a fixed set, shown on the shot's card with the exact manual steps, and one fix per group, never a guess: **Needs Copilot Credits** (an evaluation run or a generated question set), **Needs an admin screen**, **Needs another Microsoft product** (Agent Builder, Power Automate, Teams, Microsoft Foundry, Visual Studio Code), **Needs real users in a channel** (a channel, or Monitor sessions), **Needs your own connection** (a tool, data source, or service you must sign in to), **Needs another agent**, **Needs your sample files**, **Needs something built first** (a prompt, a topic, or a flow), **Needs an error to happen first**, **Outside the browser**, and **This screen has not been seen in the product yet** (hooks, triggers, "files the agent creates"). The Screenshot Center groups the count by reason (*9 need you: 3 admin screens, 2 other products, …*). A step the computer could not do on the real page also ends as needs you (its diagnostic is saved, and **Show me once** teaches the step). **Show me once** works for these steps too: Tier 3 interactions are never recorded, and a recorded write is kept only while the page is inside the practice agent. The table of every reason is in [`docs/lab-builder.md`](../../docs/lab-builder.md).

**Recipes for test conversations, dialogs, items, and a sample test set (companion 1.6.3).** Shots that used to wait for a person because "a question has to be asked first", "a dialog has to be opened first", or "this shows the details of one item" now run automatically, with generic recipes (`automation.mjs`, `families.mjs`) that the portal's plan names for each shot (`capture.automation`) and the companion checks again on this computer. Every recipe has a **ceiling of Tier 1** (open, ask, close; nothing is saved) enforced for the shot even in a job that allows a practice agent, and the same gate checks every click against the safety tiers.

| Recipe | What it does | Proven on a real tenant |
|---|---|---|
| Test conversation | Opens Preview, asks a sample question, waits for the streamed answer, and opens the panel the picture shows | The plain question and answer. The activity map and activity trace are checked by their own label. A citation, a refusal, and Track between topics are always saved as **Needs review**, because the computer cannot tell whether the screen shows them. |
| Dialog first | Clicks the button by its visible label, takes the picture, presses Cancel or Escape, and checks that the dialog closed and nothing changed (a dialog that will not close stops the run) | Add knowledge, Add tool, Add skill, Publish, the model list, and Settings. New evaluation and a button a callout names are not yet. |
| Item details | Opens the first existing item (a knowledge source or a tool), takes the picture, and leaves without saving. An item whose name sounds like something never done (an admin link, a share control) is skipped. | No |
| Sample test set | Opens the Evaluate tab; if there is no test set yet, adds one with one sample question (saved, never run) | No |
| Check by landmarks / Move by labels | For a screen that "could be in a few places", or another product's own tabs and menus: opens the closest page by visible labels (never a guessed address) and verifies by landmarks and expected labels. A miss is saved as **Needs review** with the picture and a plain reason. | No |

A recipe that was never proven is labeled in the Screenshot Center (*The computer will try this one automatically. If the screen is not what it expects, it stops and asks you.*) and fails safe: a step that does not work stops with a plain reason, the shot goes back to needing you, and after two failures of the same recipe in one job it is not tried again for other shots (no loops). The picture's screen is judged by landmarks (`image-verify.mjs` adds a `recipe-review` warning that saves the picture as **Needs review**); it is never accepted blindly and never retried. The practice agent is idempotent for the test set: the Evaluate tab is looked at first and a test set that is already listed is reused. The names of the panels come from Microsoft Learn (*Review agent activity*, *Test your agent*, *Preview overview*, *Create a test set for agent evaluation*); where a name is not confirmed on a real tenant the recipe is flagged unverified. **Spending credits is Tier 3**: controls named like **Evaluate**, **Run**, **Run evaluation**, **Generate**, or **Quick question set** are never clicked. The report is read before a run with the dry plan: `node ../lab-builder/dry-plan.mjs <generated-labs-folder> <lab id> [--all] [--json]` (or `POST /api/capture/dry-plan`).

**Slow pages are waited for, never reloaded.** The real agent page can take 15 to 20 seconds to draw its tabs. The computer opens the agent's address once, reuses the page it is on for every later step (it never opens the address of the page it is already in), and waits up to 45 seconds for the tabs without touching the page. Only if nothing was drawn after that long is the page opened once more, on purpose (at most twice in a job; the trace names it `page-recovery`). A dialog or menu that one picture leaves open is closed first (Cancel, Close, or Escape); only a fully drawn page that still shows one that will not close is opened once more (a `page-recovery` line, at most six times in a job), and then given the whole wait to draw. A shared navigation guard also refuses to open an address that is still loading or was opened in the last 45 seconds, and the trace (`--debug`) names the reason of every navigation (`navigation`) and every skipped one (`navigation-skipped`).

**Resume, reuse, and Start fresh.** The practice agent is written down on your computer (`.practice-agents.json`, never sent to the portal) the moment it exists, and a `pending` mark is written just before the one click that creates it, so a crash or a closed window can never lead to a second agent: the next run finds the agent by its name and carries on. A rerun reuses the same agent. **Start fresh** (the *Agent:* line in the readiness strip) builds a new agent on the next run and leaves the earlier one in place.

**Delete the practice agent yourself.** The computer never deletes anything. Open Copilot Studio, go to **Agents**, find the agents named `Classic shots - ...`, `Copilot shots - ...`, or (from before 1.8.0) `Lab screenshots - ...`, and delete them there (or ask an admin to). `practice-report.md` lists every item it made and the harness of each agent.

**What is verified, and where.** On the pretend site (`test/fixtures/fake-newer-layout.mjs`, `test/scratch-browser.test.mjs`): the whole flow in real Chromium, including reuse on a rerun, resume after the window closes, the new-agent page that keeps its address after Save, an account that cannot create agents, a license prompt, a limit message, an unknown dialog, a stop request, an unconfirmed account, and the older layout; with decoys and Tier 3 controls that must stay untouched. On the real Copilot Studio of a demo tenant (rounds run with the person watching): the sign-in and account guard, the default environment, creating the agent (New agent, Name, Save), finding it again by name, setting and saving the instructions, adding a public website as knowledge and saving it (each proven in the product before the stage counts as done), turning Memory on and saving it, the Preview tab with the lab's question and its streamed answer, the Agent settings tabs, the Publish dialog, publishing once to the default state, and the Build, Add knowledge, Add tool, model, and Monitor screens, all looked at picture by picture; these real-UI notes are in `docs/lab-builder.md`. Not verified on the real product: creating a Standard agent (what follows **Agent, Standard**), a proof for Home and the Agents list beyond the address host, SharePoint knowledge, creating the sample evaluation test set, and every 1.6.3 recipe except the plain question and answer and the known dialogs (the activity map and trace, item details, landmark checks, and navigation by labels have only been run on the pretend sites in both layouts, `test/scratch-browser.test.mjs`, `test/fixtures/fake-newer-layout.mjs`, and `test/fixtures/fake-product-site.mjs`; a real-tenant round proves them). Evaluation runs use Copilot Credits and are never done.

### Signing in once per product

The companion never types a password or clicks a sign-in button. You sign in yourself, and it only watches the address bar to know when you are done.

- **While you sign in, it only watches.** Once the browser is on a Microsoft sign-in page (or your company's identity provider), the companion makes no navigation, reload, retry, click, or picture until the page has left the sign-in pages and stayed on the product. Then it keeps watching several more seconds, because many apps finish signing in with one more round trip (a live Copilot Studio sign-in took about 13 seconds after the sign-in page to reach the home page, with pauses of about 4 seconds between pages). Every navigation it does make is written to the trace with its reason (`--debug`).
- **The first page of a product is watched for about 10 seconds.** The real products show their own page for several seconds (about 6 for Copilot Studio) and only then send the browser to sign in, so a quiet first page is not proof of a signed-in session. This happens once per product per job. After a fresh sign-in lands on the product's home page, the companion opens the screen it was asked for once.
- **One sign-in wait per product per job.** When a page turns out to be the Microsoft sign-in page, the companion waits for you (up to `--sign-in-wait` seconds), prints one message, and tells the portal. It waits through **Stay signed in?**, the account picker, multi-factor prompts (a 20-second wait for a phone approval is fine), consent pages, and **Working on it** pages. A quick silent trip to the sign-in page, a page that redirects to sign-in a moment after it loads, and a signed-in page whose address merely mentions a sign-in address are all handled without bothering you.
- **A sign-in that loops is stopped and explained.** If the browser bounces between the product and a sign-in page three or more times within 90 seconds without ever staying on a sign-in page long enough for you to type, the companion stops, leaves the window open so you can look at it, and prints the likely causes: sign-in files in a synced folder, blocked cookies, Conditional Access that wants a managed device or a particular browser, a wrong clock, a stale saved sign-in, blocked pop-ups, and the `AADSTS` error number if Microsoft shows one (an error number is not a secret; no other page text is read). The portal shows the same verdict and the next step.
- **A sign-in nobody finishes is not called a loop.** If the sign-in page just sits there (no page changes, no bouncing) until the wait runs out, the first thing the companion says is that the sign-in page was waiting for you, and what to do in that window. `--sign-in-wait=<seconds>` allows more time.
- **The window can open behind your other windows.** Windows does not let a program started in the background take over the screen, so the sign-in window may open behind the window you are using, which looks like a sign-in box that vanished. A live run showed exactly this: the window was behind other windows for most of the sign-in. The companion asks the browser to come forward once when it starts (Windows may still keep it behind, and a test showed it often does), then never again, so it will not take focus while you type. It says where to look in the console and the portal ("look for the new browser window on the taskbar"), and `--check-signin` records whether the window was covered.
- **If sign-in does not finish, it stops.** The rest of that product's shots are reported once, right away, as needing a sign-in (the portal shows **Sign in to <product> on your computer, then retry the N screenshots**). The companion does not reopen the sign-in page for every shot.
- **Choose Yes on "Stay signed in?"** Without it, Microsoft keeps the sign-in in a session cookie that a closed browser throws away. The companion saves those cookies itself after every successful capture and restores them the next time, but **Yes** makes the sign-in last across restarts without relying on that.
- **Each product has its own sign-in.** Copilot Studio, Agent Builder, SharePoint AI, Microsoft Foundry, the Microsoft 365 Copilot hub, and the Power Platform AI hub each use their own browser profile, so a lab that spans two products asks you to sign in to each one once. Each browser kind (Edge, Chrome, Chromium) also has its own profiles.
- **Never clicks anything that signs in or out.** It refuses controls named Sign in, Sign out, Log in, Log out, Switch account, Use another account, Add account, Remove account, and the account and profile menus, however the plan names them, and it checks the link behind a control as well.
- **Pausing and stopping in `--watch` mode.** After a job ends without a sign-in, the companion waits 30 seconds before taking another job (60 seconds after a second one). After three jobs in a row that ended without a sign-in for the same product, it stops taking jobs and tells you why, so it cannot loop. Fix the sign-in, then start it again. A job the portal hands back after the companion already ran it twice is closed instead of run again.

#### Where the companion keeps its data

Since version 1.4.0 the pairing file, browser profiles, traces, recipes, and the practice-agent list live in a **local folder of your user account**, never beside the code:

| System | Default data folder |
| --- | --- |
| Windows | `%LOCALAPPDATA%\CopilotStudioLabsCompanion` |
| macOS | `~/Library/Application Support/CopilotStudioLabsCompanion` |
| Linux | `${XDG_DATA_HOME:-~/.local/share}/copilot-studio-labs-companion` |

Why: a live browser profile has a locked cookie database and files that change all the time, and a saved sign-in lets anyone who has it act as you. OneDrive, Dropbox, iCloud Drive, and Google Drive can lock or lose those files (the sign-in never sticks and loops) and upload the sign-in to the cloud. Unzipping the companion into your Documents folder (which OneDrive often syncs) is fine now, because only the code lives there.

- **Synced folders are refused.** `--home=<folder>` and `COMPANION_HOME` still work, but if the folder is inside OneDrive, Dropbox, iCloud Drive, Google Drive, or Box (found from the folder names on its path, the `OneDrive`, `OneDriveCommercial`, and `OneDriveConsumer` environment variables, the macOS `CloudStorage` folder, and on Windows the read-only reparse-point attributes that OneDrive Files On-Demand sets), the companion refuses to start and prints the exact command with the local folder. `--allow-synced-home` overrides that (not recommended). `--status` and `--check-signin` show where the data is and warn about a synced folder.
- **Moving from an older version.** On the first start the companion copies the pairing file, settings, practice list, and recorded recipes from the old place (beside `companion.mjs`) into the local folder. If the old folder is synced, the pairing file is moved so the token does not stay in the cloud. The browser profile is not copied (it may be damaged), so you sign in once more. A small saved-session file is kept when the old folder was not synced. The old `.auth` folder is never deleted without being asked: run `node companion.mjs --delete-old-signin` (or answer **y** when it asks).

#### How the browser is started

By default (`--launch=auto`) Edge and Chrome are started **the normal way**: the companion runs your installed browser as an ordinary program with its own profile folder in the data folder and a debugging port, then connects to it. The port is random and listens on `127.0.0.1` only, and it closes when the browser exits. The companion does not add the switches Playwright's own launcher adds (the "controlled by automated test software" bar, disabled extensions, and others), because some organizations' device-based sign-in (Conditional Access that wants a managed or compliant device, Windows work-account single sign-on) does not work in a browser started that way, and the sign-in bounces. Nothing is hidden: the browser reports itself as it always does, and you sign in by hand.

- `--launch=playwright` uses Playwright's launcher (the previous behavior). `auto` falls back to it with one message if the normal start fails (never when the browser profile is in use, see below); `--launch=attach` never falls back. The fallback message adds "If your organization needs a managed browser, sign-in may not work." only on a PC that has a Windows work account.
- The bundled Chromium is always launched by Playwright. `--headless` and `--background` use a hidden window of the same browser.
- One companion per profile: a second one is told to wait. The browser the companion starts is ended when the job ends, when you press Ctrl+C, when you close the console window, and when the companion crashes. While it runs, the profile folder holds `.companion-browser.json` (the browser's process number and debugging port, nothing else); it is removed when the browser exits.
- The companion never opens a browser on the folder your own browser uses every day (for example `%LOCALAPPDATA%\Microsoft\Edge\User Data`). A `--home` that would lead there is refused.

#### When the capture browser is already in use

A browser started on a profile folder that another browser process already has does not open a window: it hands the request over and exits. Earlier versions then tried the automation launcher, which failed the same way, and reported every screenshot as failed. Now the companion looks **before** it starts a browser, with no administrator rights:

1. It reads the browser programs that are running (Windows: `Win32_Process` through PowerShell; macOS and Linux: `ps`) and finds those whose command line names this exact profile folder.
2. It reads the profile's own lock (Windows: the `lockfile` the browser keeps open; macOS and Linux: `SingletonLock`), a `DevToolsActivePort` file whose port still answers, and its own `.companion-browser.json`.

Then one of these happens:

| What it finds | What happens |
| --- | --- |
| Nothing holds the profile | The browser starts as usual. |
| A browser **this companion started earlier** is still running and answers on its debugging port (for example after a crash) | The companion connects to it instead of starting another. It counts as started here only with proof: the recorded process number and port match a live program whose command line names this profile folder and that port. A hidden browser that a window is needed for is asked to quit politely first. |
| That browser is still running but does **not answer** | The companion tells you which window to close, waits, and carries on by itself when it is gone. It never closes it for you. |
| A browser it **cannot prove it started** holds the profile (your own window, a window from an older version, a program it cannot see) | The same: it says what to close (`A browser window from an earlier run is still open on the capture profile. Close the Microsoft Edge window that the capture tool opened ...`), leaves the program alone, and waits. Your everyday browser windows are never involved, because they use a different folder. |
| Another companion on this computer is using it | It says so and waits for that one to finish. |

While it waits it prints one line every 15 seconds (`Still waiting for the capture browser to be free (30 of 120 seconds) ...`) and the same text appears in the portal's live progress. After two minutes the job ends as **waiting for the browser**: the screenshots are reported as paused (cause `browser-busy`), not failed, nothing is created or published, the practice-agent records are not touched, and **Resume** in the portal queues them again. A start that fails with "profile in use" although nothing could be seen is tried at most three times, ten seconds apart, because each try can open a window in the browser that has the profile. The raw browser text (for example `Opening in existing browser session`) goes to the `--debug` trace only.

#### Checking a sign-in that will not stick

```powershell
node companion.mjs --check-signin                 # Copilot Studio
node companion.mjs --check-signin=ai-foundry      # another product
```

It opens the product's start page once, then only watches while you sign in, and prints a verdict in plain language: the sequence of pages (host and path only, never query strings) with timings, whether the browser was started the normal way, whether this computer is joined to a work or school account (yes or no, from `dsregcmd`), which sign-in and product cookies exist (names and attributes such as `Secure`, `HttpOnly`, and whether they survive closing the browser, **never values**), whether the browser profile blocks cookies, whether the data folder is synced, how far this computer's clock is from Microsoft's, and any `AADSTS` error number. The same text is written to a redacted trace under `.captures/traces/check-signin-<time>.log`, which has no query strings, cookie values, tokens, page text, or account and tenant names, so you can send it to whoever helps you.

The check also records what the browser **window** did, without reading any page text and without touching the window: how many windows and tabs there were, whether a popup opened or a tab closed, whether the window was minimized, whether the sign-in page rendered its form or went blank (counts of elements and inputs only, never their text), whether the page title was empty (never the title), and, on Windows, whether the window was in front or covered by another program, and whether a Windows sign-in window (such as the credential or account broker) was open. Only a short list of sign-in broker program names is ever reported; any other program is just "another-app". This is the `Window:` line in the verdict and the `surface-*` events in the trace.

**What is saved.** In the data folder, `.auth/<browser>/<product>/` (or `.auth/separate/<browser>/<product>/` for a separate sign-in on a PC with a Windows work account) holds the browser profile, `companion-session.json` (your browser's cookies for that product, including session cookies), `companion-signin.json` (when it last worked), and `companion-account.json` (yes or no flags about the account: how it was chosen, whether it was verified or confirmed, whether it is the account Windows uses for work; never a name, a tenant id, or an address). **Anyone who has these files can act as the signed-in account**, so keep the folder private. They stay on this computer, are git-ignored, and are left out of the companion download and the container image. To start over for one product run `node companion.mjs --forget-signin=copilot-studio`, or for everything `--forget-signin=all`. You can also delete the product's folder under `.auth/` yourself. Folders from older versions, such as `.auth/copilot-studio/`, are not used by the companion any more; delete them if you like.

### Which account the screenshots come from

A screenshot shows whatever account the browser is signed in with. For a lab that is almost always your **demo tenant**, not the account your computer signs in with at work. Screenshots from a work tenant would also be uploaded into your labs and exports, which is a privacy risk, so the companion makes the account **explicit, correct, and verified** before it takes a picture.

**Why this needs care.** A Windows PC joined to a work or school account (Microsoft Entra) has a *Windows work account*. Microsoft Edge can use it: on a managed PC Edge signs its profiles in with that account (often forced by an organization policy), and on a Microsoft sign-in page it can offer that account with one click or sign in with it by itself. Browsers that have no Windows account integration (Chromium from Playwright, Google Chrome without the Windows Accounts extension) just show the normal sign-in page, so you choose the account.

**What the companion does by default.**

1. At start it reads, on Windows, whether this PC has such an account (`dsregcmd /status`: Entra joined, work account added, domain joined, and whether a sign-in token exists). It keeps only yes or no. If Windows does not answer in time, the companion asks once more with a longer wait, then uses the yes or no from an earlier start (`.companion-os-account.json`, a yes or no and a date) or the fact that a separate sign-in already exists here, and says so in the console, so one slow answer never sends a capture to the shared sign-in. The Windows account's tenant id is used in memory to compare and is never printed, traced, uploaded, shown, or saved.
2. If it has one, `--account-mode` defaults to **`separate`**: the companion never takes the Windows account on its own. `--browser=auto` then tries **Google Chrome, then Chromium, then Microsoft Edge opened InPrivate** (an InPrivate window has no browser profile, so it does not carry the Windows account). Without a Windows work account (or on macOS and Linux, where it cannot tell) nothing changes: Edge, then Chrome, then Chromium.
3. A `separate` sign-in has its own profile folder (`.auth/separate/<browser>/<product>/`), so a profile that was signed in by the Windows account (the original `.auth/<browser>/<product>/` folders) is **never reused** as a separate one. You sign in once, yourself, with the account you want. The companion remembers it on this computer.
4. After sign-in, before the first screenshot of each product, it checks which account this is and stops with one plain sentence if it is wrong (see below). The console says at the start what each choice does.

| Option | What it does |
| --- | --- |
| `--browser=auto\|edge\|chrome\|chromium` | Which browser. The explicit choice is never changed, but in `separate` mode on a PC with a Windows work account Edge is opened InPrivate. Quick fix if Edge picked your work account: `--browser=chromium`. |
| `--account-mode=separate\|windows` | `separate` (the default when the PC has a Windows work account): you sign in yourself and the Windows account is never taken silently. `windows`: allow the old behavior **on purpose**: Edge opens normally and may sign in with your Windows work account, and screenshots then come from that account. The console and the Screenshot Center say so. |
| `--setup-account[=<product>]` | Choose the account: opens the browser on the dedicated profile at the product's start page and tells you to sign in with the account you want. See below. |
| `--forget-signin=<product>\|all` | Removes every saved sign-in of the product, in both profile layouts (separate and original). |

**Choose which account to use.** Run `node companion.mjs --setup-account` (or select **Choose which account to use** in the Screenshot Center, which asks the connected companion through its next check-in, so a window opens on your computer within a few seconds). The companion starts from a clean sign-in profile so you are shown a sign-in page, opens the product, and says what to do. **You** sign in with the account you want; if the browser shows a list of accounts (or **Use another account**), **you** pick. The companion never clicks, types, or picks an account: it only watches the address bar, like for every sign-in. When the page lands, it checks it (below), records that you chose the account, saves the session on this computer, and closes the window. If an account list shows, it simply waits.

**How it knows which account this is (never by reading page text).** After sign-in each profile gets one of these labels, kept as a flag in `companion-account.json` next to the profile:

| `account.source` | Meaning |
| --- | --- |
| `windows-sso` | No sign-in page was shown (a redirect to the sign-in host that passes in about a second or two) **and** the page landed in the Windows work account's own tenant (the `Default-<tenant id>` part of a Copilot Studio environment address, or a tenant id in a product address). |
| `manual` | A sign-in page stayed long enough for a person to use it (three seconds or more) and was completed. |
| `saved-session` | A sign-in saved on this computer was restored with no sign-in page, and it does not land in the Windows tenant, or the profile was classified before. |
| `unknown` | None of these can be told (for example, a product address that has no tenant id in it). |

The companion also keeps `inOsTenant` (a yes or no): whether the account is the same one Windows uses for work. Both labels and the yes or no are all that is ever reported. If you sign in yourself with your work account, `source` is `manual` and `inOsTenant` is yes: allowed, because you chose it, but the Screenshot Center warns that screenshots will come from that account.

**The wrong-account guard.** Before the first screenshot of each product the companion opens your own address when the job carries one (the Copilot Studio agent or environment address, the SharePoint site, a Power Platform environment, a Foundry project) and compares where the browser landed (host and path only, plus whether the page title is empty), without reading page text:

- **`windows-sso` in `separate` mode** stops the product with: *Edge signed in automatically with your Windows work account, not the account that owns this agent. Restart with --browser=chromium, or run --setup-account.* With `--account-mode=windows` it is allowed on purpose, unless it does not fit your address, which stops too.
- **The address leads somewhere else** (another environment id, another SharePoint host, an access-denied or not-found page, the agent never opened) stops with: *You are signed in to a different account than the one that owns that agent. Run --setup-account and sign in with the account you want, then retake.*
- **Addresses not set.** The job may still run, but the readiness strip says **Account not verified**. **Automatic capture does not start**, even with consent, until the account was verified against one of your addresses or you confirmed it once with `--setup-account` (only a yes or no is stored). A name (an agent name) is not an address.

A stop is reported to the portal as the shot status `needs-account` (a failed shot with the cause *Signed in to the wrong account*). The Screenshot Center shows the one-sentence fix and a **Choose which account to use** button.

**How to check which account is in use.** `node companion.mjs --status` shows the account line and, for each profile, how its account was chosen and whether it was verified; `--check-signin` prints the same after a sign-in; the Screenshot Center shows **Account: separate sign-in (browser: Chromium), verified for your agent.**, or **Account: your Windows work account (Edge single sign-on). Screenshots will come from that account.** with a warning and the fix button, or **Account not reported (update the companion)** for a companion older than 1.5.0. Nothing shows a tenant id, an address, or an account name.

**Measured on a work-joined PC** (fresh throwaway profiles, headed, nothing signed in, only the hops and timings observed). On that PC Edge was configured by policy to sign every profile in with the work account.

| Mode | Sign-in page shown? | What it offered |
| --- | --- | --- |
| Edge, normal (attach, or Playwright's launcher) | yes (it did not finish by itself in repeated runs) | an account list with the Windows work account one click away |
| Edge InPrivate | yes | an empty sign-in box, no Windows account |
| Chromium from Playwright (attach or launcher) | yes | an empty sign-in box |
| Google Chrome | not measured: not installed on that PC | |

Silent sign-in in Edge on a work-joined PC did not happen in these runs, but it can happen (it depends on the organization's policies and on timing), so the companion never relies on this: it classifies the result afterwards. That is why the default avoids a normal Edge window when a Windows work account is present.

#### Browser differences that matter for pictures

The companion normalizes these so a picture is the same in every browser. Measured with Edge and Chromium on a 150% display scale:

- **Size and display scaling.** Before the viewport is set, Edge's page was 1.5 times larger (1542 by 1362 pixels). The companion sets the viewport to 1440 by 900 CSS pixels at a device pixel ratio of 1 before every shot, reads it back (`viewport` in the trace), and sets it once more if it did not take. Pictures are 1440 by 900 pixels in Edge and Chromium. The visible window is also resized toward the picture size, as far as the screen allows, so a screen you set up yourself is not cropped.
- **A window that another window covers.** A browser started the normal way throttles a covered window, and a picture of it can hang (it did in Chromium; Edge was not affected). The companion adds three documented switches that only turn that throttling off for hidden windows (`--disable-backgrounding-occluded-windows`, `--disable-renderer-backgrounding`, `--disable-background-timer-throttling`). They change nothing about how the browser identifies itself. A **minimized** window cannot be captured in any browser (the picture times out): keep the window open, not minimized.
- **Extra tabs.** A new browser profile opens, closes, and replaces its own first tabs; the companion waits for that to settle and closes the browser's own leftover pages (`edge://`, `chrome://`, `about:`) before each shot. It never closes a page of the web (a sign-in popup, a product tab). `--no-first-run` and `--no-default-browser-check` keep the welcome pages away.
- **Edge extras that do not matter.** The sidebar, the Copilot panel, shopping and coupon bubbles, sign-in-to-sync prompts, and translate bubbles are browser interface, not page content, so they are not in the picture.

### Security model

- **Paired, scoped, revocable.** A one-time code is traded for a capture token (`cap_...`). The portal keeps only a hash of the code and the token, compares them in constant time, extends the token while you use it, and lets you disconnect the computer at any time. The token opens only the companion endpoints; it is not a portal sign-in and cannot read or change anything else. A revoked or expired token is refused and the companion tells you to pair again.
- **Nothing secret in the download or in git.** The portal's download and this folder contain no tokens. The pairing file `.companion.json`, your browser sign-ins (`.auth/`, including the saved session cookies), and in-progress captures and traces (`.captures/`) stay on your computer, are git-ignored, and are left out of the companion download and the container image. The token is saved with owner-only permissions where the system supports it and is never printed.
- **Your credentials never leave your computer.** You sign in yourself in a real browser window. Only screenshots, page addresses (without query strings), the page title, and visible control names are sent, and only to the portal you paired with. Portal addresses must be `https` (`http` is allowed for `localhost` only).
- **It never types into tenant pages and never changes the tenant.** Steps are limited to opening an `https` page, waiting, dismissing banners, and clicking an exact-name navigation item or tab. It skips any control whose name says delete, remove, erase, purge, destroy, disconnect, unregister, revoke, or reset, any control that creates or changes something (Publish, Create, Save, Submit, Add, Edit, and similar, or a button that submits a form), and any control that signs in or out or switches the account (Sign in, Sign out, Switch account, Use another account, the account menu), whatever the portal asks for. It does not change how the browser identifies itself or hide that it is automated; it uses a normal installed browser that you sign in to yourself.
- **Account details are hidden.** Before each picture it draws a solid block over the account control (including the account menu of the newer Copilot Studio layout), over the environment picker (its label carries the environment's name), over the name in a greeting such as *Hey <name>, ready to ...* on the Home page, and over any email address, tenant host name (`*.onmicrosoft.com`, SharePoint admin and personal hosts), or `--mask` term on the page, then removes the blocks. Text sent to the portal as evidence is scrubbed the same way. A diagnostic file keeps control names but drops the person or environment named in a label such as *Open account menu for ...*. Look at every screenshot before you publish it: the Home page also lists the agents you opened last, and other pages can show other people's names, so use `--mask` for names you want covered.
- **Verified twice.** Both the companion and the portal check magic bytes (PNG, JPEG, WebP), size (5 KB to 8 MB), dimensions, blank or sign-in pages, placeholder pictures, and a match with the expected control names. The portal never trusts what the companion reports for a security decision.
- **Tenant addresses.** A job can carry `CAPTURE_*` addresses (https only) for your tenant, for example from the lab's brand profile. They override same-named variables on your computer for that job only.

### Troubleshooting

| What you see | What to do |
| --- | --- |
| `The Playwright package is not installed` or `The Chromium browser is not installed` | In this folder run `npm install` then `npx playwright install chromium`, or run with `--install-browser`. |
| `Node.js 20 or later is required` | Install a current Node.js LTS from nodejs.org. |

## Usage

```powershell
npm run capture              # capture shots missing on disk
npm run list                 # show existing/missing shots
node capture.js --help       # show all flags and keystrokes
node capture.js --dry-run --missing  # validate catalog without launching Playwright

node capture.js --range=5-10 # capture an inclusive ID range
node capture.js --from=5     # start at shot ID 5
```

Selection precedence is `--only` > `--range` > `--from` > `--missing` default; conflicting selection flags are rejected.

### Verify screenshot consistency

```powershell
npm run verify
node verify-shots.js --lab=06-energy-weather-agent
node verify-shots.js --json
node verify-shots.js --strict
```

`verify-shots.js` scans lab markdown, `shots.json`, and lab assets for schema drift, missing or invalid image files, markdown/catalog mismatches, placeholder pictures, tiny placeholder-like PNGs, and orphan PNG/JPEG assets. It exits `0` when there are no critical findings, `1` when critical findings exist; `--strict` also fails on warnings.

A lab image that is a placeholder picture (the neutral "Screenshot pending" image, or a captioned filler such as the "PLACEHOLDER SCREENSHOT" pictures) is reported as a `placeholder-image` warning with the line that shows it. `node verify-shots.js --check-state` goes further and reports a CRITICAL `restored-placeholder` finding for any filler picture in any lab's `assets/` folder, so a restored or regenerated placeholder cannot be committed as if it were a capture. The pending image is the intended stand-in for a missing capture and stays a warning.

### Placeholder detection

`placeholder-detect.mjs` is the one detector every check here uses (`capture.js --missing`, `verifyCapturedImageBuffer` in `lab-runner.mjs`, `verifyImage` in `image-verify.mjs`, `verify-shots.js`, `status.mjs`, and the feature tour). It imports only Node built-ins and ships in the companion download, so the companion and the portal give the same answer. Run it on any file to see the verdict and the file's SHA-256:

```powershell
node placeholder-detect.mjs path\to\picture.png
```

A picture is a placeholder when it carries the `Software=cslabs-placeholder` PNG text entry (the scripts that draw placeholders stamp it), when its SHA-256 is in `KNOWN_PLACEHOLDER_SHA256`, when it is the neutral pending image, or when its layout matches a placeholder generator. The file size never decides it. To teach it a new file, add its SHA-256 to `KNOWN_PLACEHOLDER_SHA256` and the file to `test/fixtures/placeholders/`; see [Placeholder pictures never count as screenshots](../../docs/lab-builder.md#placeholder-pictures-never-count-as-screenshots).

## Heads-up: commit deletions promptly

Deleted Lab 06 placeholder PNGs still exist in git history. `git restore`, VS Code **Discard Changes**, or **Discard All Changes** can restore them into the working tree; run `node verify-shots.js --check-state` before committing screenshot changes.

> ⚠️ **Heads up:** npm 11 strips unknown flags like `--all` from `npm run capture -- --all`. Use the direct `node capture.js …` form when passing flags. `npm run capture` and `npm run list` are wired in `package.json` so they work as-is.

## During a capture session

Get the browser into the right state, then use the terminal keystrokes shown in the one-line prompt:

- `Space` — snap, verify, save, and advance
- `r` — retry/re-snap the current shot after you tweak the UI
- `n` — skip this shot without saving
- `q` — quit gracefully, close Chromium, and persist auth
- `?` — re-print the current instructions

Each exit path prints snapped/skipped/retried/failed-verify counts and the remaining missing filenames.

## Optional `shots.json` fields

Each shot still requires `id`, `filename`, `section`, and `instructions`. Optional fields are:

```json
{
  "section": "topics",
  "url": "https://copilotstudio.microsoft.com/...",
  "labSection": "Use Case #1, Step 2",
  "viewport": { "width": 1440, "height": 900 },
  "zoom": 1.0,
  "highlight": { "selector": "[data-id='target']", "label": "Future callout" }
}
```

`url` navigates before prompting when the active page is elsewhere. When `url` is absent, `section` is treated as a current-agent section such as `topics`, `actions`, `agents`, `settings`, or `evaluations`; if the browser is already under `/environments/.../bots/.../`, the tool keeps the current environment/agent and replaces only the trailing section. Absolute `url` values win over `section`. If no current agent is open, the tool prints a hint and waits for manual navigation. `labSection` keeps the human lab step label for prompts. `viewport` and `zoom` reset to 1440x900 / 1.0 between shots before applying shot overrides. `highlight` is reserved for future callout-arrow work and is not implemented yet.

## Notes

- Login state for the interactive `capture.js` tool is stored in `tools/screenshot-capture/.auth/` (feature tour: `.auth/<product>/`). That directory is git-ignored — never commit it. The Local Capture Companion keeps its own sign-ins in `.auth/<browser>/<product>/` (see [Signing in](#signing-in-once-per-product)), so a sign-in made with one tool is not shared with the other. Its pairing file `.companion.json` and `.captures/` are git-ignored too.
- PNGs land directly in `labs/06-energy-weather-agent/assets/` with filenames declared in `shots.json`.
- The default manifest is currently configured for Lab 06. Use `--manifest=<path>` for another lab instead of rewriting the default catalog.
- Tests (`node --test "test/*.test.mjs"`) are hermetic: they run `--dry-run`, use temporary fixture images and a fake Playwright, so they need neither a browser nor a tenant. `test/signin-real-browser.test.mjs` also drives a real Chromium (and Microsoft Edge when it is installed) against a pretend tenant that answers by route interception, and skips itself when no browser is installed. `node test/fixtures/signin-repro.mjs [--tool-dir=<folder>] [--channel=msedge]` prints the sign-in scenarios as a table, which is how a before and after comparison is made.
